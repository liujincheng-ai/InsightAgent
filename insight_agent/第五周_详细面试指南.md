# InsightAgent 项目面试文档（第一至第五周）

## 一句话定位

InsightAgent 是基于 InsightAgent 二次开发的企业经营分析 Agent：把汽车配件销售数据库、指标
口径和企业制度接入同一 ReAct 流程，用确定性 Tool、SQL 语义门禁、RAG 引用、有限重试
和上下文预算解决“会调用但不可靠、能生成但不可追溯”的问题。

## 1 分钟介绍

我独立完成了一个企业经营分析 Agent。它可以根据自然语言查询 PostgreSQL，做销售下降
归因、客户流失预警和经销商健康评分，再检索企业制度并生成带引用的 HTML 报告。项目
不是只接了一个模型 API，我重点改了五层可靠性：第一周做 Text-to-SQL 业务语义层和
歧义门禁；第二周做 Tool Schema、ReAct 协议兼容和隔离评测；第三周做跨文档 RAG、引用
和拒答；第四周做统一错误分类、一次共享恢复预算和有界终止；第五周做上下文预算、大
结果落盘和成本评测。最终第五周 Flash 冻结集从基线 12/20 提升到 15/20，关键事实 95%、
引用 95.45%，平均估算输入 Token 和成本分别下降 50.01% 与 47.90%，没有上下文溢出。

## 3 分钟介绍

项目场景是汽车配件销售公司的经营分析。底层有 6 万条合成销售明细、6 份带固定章节号
的制度、PostgreSQL、Chroma 和本地中文 Embedding，生成模型用 DeepSeek。

我把系统拆成三类职责：LLM 做意图理解和流程决策；领域 Tool 用参数化 SQL 确定性计算
同比、环比、加权毛利率、渠道下降贡献、风险客户和健康评分；控制层负责参数校验、只读
安全、证据顺序、重试预算、完成条件和上下文预算。这样核心经营数值不让模型临时计算，
制度结论也必须绑定文档与章节。

五周中最重要的工程闭环有三个。第一，Text-to-SQL 不只校验语法，还校验业务语义，例如
毛利率必须是总毛利除以总销售额，贡献率必须使用整体净下降作为分母，歧义问题先澄清且
当轮不挂 SQL Tool。第二，Tool Calling 失败不全是模型能力问题：Week 2 首轮 Pro 只有
14/40，轨迹显示大量答案已经选择正确 Tool，但用了 JSON ReAct、一行式或全角冒号，原
解析器不兼容；修复协议后同集回归 38/40。第三，长链路不能无限堆上下文。我收敛综合
模式工具面，把大 SQL 完整结果先落盘，只在上下文保留 Schema、总行数、Top-N 和路径，
再用分层预算监控旧 Observation、历史轮次和输出预留。

评测上我坚持保留失败：Week 3 自动事实 81.90%、人工复核 92.86% 同时报告；Week 5
唯一 Pro 终验只有 9/20，也原样保留。这让我能解释模型、协议、工具面和完成合同之间的
耦合，而不是只给一个最好看的数字。

## 8 分钟展开

### 1. 场景和目标

传统问数系统容易出现四类问题：SQL 能执行但口径错；模型选错 Tool 或参数非法；制度
引用无法回查；长链任务在重复 Observation、检索片段和报告 HTML 中快速膨胀。项目目标
不是替代 BI，而是验证一个“数据事实—规则判断—管理建议”分层、可审计的 Agent 原型。

### 2. 主链路

```text
HTTP/SSE 请求
  → 识别数据库、知识库和任务模式
  → 构建聚焦 Prompt 与受控 ToolPack
  → 领域 Tool / 只读 SQL 获取事实
  → RAG 检索制度文档与章节
  → HTML 报告
  → 完成合同校验
  → 确定性事实呈现与结构化引用
```

关键源码：

- API 与 SSE：`packages/dbgpt-app/src/dbgpt_app/openapi/api_v1/agentic_data_api.py`
- Agent 上下文：`packages/dbgpt-core/src/dbgpt/agent/core/context/`
- 流程门控：`insight_agent/agent/sales_diagnosis_gate.py`
- 语义与呈现：`insight_agent/agent/domain_policy.py`
- 三个领域 Tool：`insight_agent/tools/`
- 评测：`insight_agent/evaluation/`

### 3. 第一周：Text-to-SQL 语义可靠性

我将指标公式、单位、时间半开区间、Join 方向和歧义规则放入 YAML 业务词典，并按问题
动态选择相关语义，而不是把整个词典塞入 Prompt。SQL 进入数据库前还要经过只读、单语句
和业务预检。唯一 Pro 正式运行 27/30；SQL 执行、歧义处理和澄清前不查库均为 100%。

典型问题是渠道贡献率。模型曾把下降渠道之和当分母得到 73.99%，正确口径应使用区域
品类整体净下降，结果是 74.89%。我没有对问题写固定答案，而是修正通用公式和确定性
呈现，再用回归题验证。

### 4. 第二周：Tool Calling 与协议兼容

三个业务 Tool 使用 Pydantic Schema 约束区域、品类、季度、阈值和 Top-N，未知字段和
非法参数在访问数据库前被拒绝。评测模式与生产兜底分离：前者看模型自主选择，后者看
用户任务能否可靠完成。

首次 Pro 14/40 不是简单的“选错工具”。24 条选择失败中有 23 条没有形成可执行 Action，
主要是输出格式超出解析器。兼容明确 Action 的 JSON/文本变体后，同集回归 38/40，Flash
boundary 选择准确率 99.17%、参数有效率 100%。我会主动说明这是看过失败后的修复回归，
不是独立盲测。

### 5. 第三周：RAG、引用和拒答

我构建 40 题冻结集和 4 份旧版/外部干扰文档，对 Vector、BM25、3 个 Chunk Size、3 个
Overlap、3 个 Top-K 做 54 组矩阵。最终采用中文 BGE、Chroma、512/50、Top-5，加确定性
多意图拆分和跨文档 RRF 扩展。Pro 的文档命中 100%、MRR 98.10%、引用精度 100%、
拒答 5/5、伪造引用 0；自动事实 81.90%，人工逐题复核 92.86%。

### 6. 第四周：错误恢复与完成合同

统一分类 SQL、Schema、RAG、超时、权限等失败；只对可恢复错误开放请求级一次共享预算，
相同失败指纹阻断，权限和未知错误失败关闭。完成状态区分 success、partial、failed，不能
因为最后调用了 terminate 就把任务算成功。Pro 原始可恢复任务恢复率 66.67%，同集修复
回归 91.67%，有界终止 100%，盲重试 0。

### 7. 第五周：上下文和成本

我修复了 Layer 3 使用未初始化模型名、配置未接入模型元数据、逐轮工具预算未调用、SQL
先截断后声称可追溯等问题。大结果现在完整落盘，模型只看摘要和路径；综合模式从通用
大工具集收敛为必要工具集合，多领域题必须完成所有显式 Tool。

20 题 Flash 正式聚合为 15/20，关键事实 95%、引用 95.45%，平均估算输入 Token 从
49,612.95 降到 24,800.55，成本从 0.107047 元降到 0.055766 元，平均延迟从 12.376 秒
降到 8.204 秒，无溢出。唯一 Pro 只有 9/20，说明更贵模型不一定更适配当前编排协议。

## 高频追问与回答

### 为什么不用 LangGraph？

项目目标是验证 InsightAgent 原有 Agent 扩展点能否承载可靠性控制。现有 ToolPack、Memory、
Action 和 SSE 已足够实现状态门控、重试预算与上下文管理；引入新框架会扩大变量。若后续
出现跨进程持久状态、人工审批和复杂 DAG，再考虑迁移。

### 为什么核心指标放 Tool，不让 LLM 算？

同比、加权毛利率和贡献率有稳定公式且需要审计。LLM 适合理解意图和组织语言，不适合
承担必须精确复现的数值计算。把稳定逻辑下沉到 Tool，能测试、回归和版本化。

### 如何防 SQL 写入？

三层：Prompt 只声明只读；执行前做单 SELECT/CTE 预检并拒绝 DML/DDL；PostgreSQL 使用
独立只读角色和只读事务。数据库权限是最终防线。

### Token 是怎么统计的？

服务没有返回供应商 Usage，因此评测器读取每次模型调用前的 `context.status.used`，再加
问题与输出的本地估算。报告明确标为估算，不能冒充真实账单。

### 为什么正式轨迹没有触发压缩层？

工具面收敛和结果落盘已把上下文控制在阈值内，说明更早层的治理有效。四层压缩有单测，
但本轮运行没有达到触发条件；因此不能把 50.01% 降幅归因于摘要压缩。

### 为什么补跑可以计入验收？

只有网络异常、无证据占位输出和有确定性修复/单测证据的呈现缺口允许固定一次补跑；主
运行和补跑都保留，并明确称修复回归。不能静默重复直到得到好结果。

### 如何看待 Pro 比 Flash 差？

Agent 任务成功率取决于模型与协议、Prompt、工具描述、门控和终止策略的组合。Pro 更倾向
主动改写或扩展动作，在严格文本 ReAct 和有限步骤下可能更容易偏离。模型选型必须按任务
评测，不能只按单价或名称。

### 大数据开发面试时怎么讲？

重点不是声称用了 Spark/Flink，而是讲数据口径、事实表与维表、只读 PostgreSQL、聚合
View、增量可追溯结果、质量校验、冻结数据集和可复现评测。Agent 是数据消费与编排层，
数据正确性和治理仍是主线。

### 国企面试时怎么讲？

强调数据不出边界、只读权限、制度依据、审计轨迹、错误脱敏、有限重试和不夸大结论；
同时诚实说明当前是合成数据单机原型，RBAC、多租户和生产审计仍未完成。
