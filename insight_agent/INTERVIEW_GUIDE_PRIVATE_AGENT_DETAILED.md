# InsightAgent 完整面试文档（私企 Agent 开发岗）

## 1. 面试定位

这个项目的亮点不是“重写 InsightAgent”，而是理解并复用真实 Agent 调用链，再用可测量的业务 Tool、门禁、失败恢复和 Benchmark 解决垂直场景的不稳定问题。

## 2. 3 分钟讲稿

我做的项目叫 InsightAgent，是一个企业经营分析 Agent，首个场景是汽车配件销售。它要解决的问题是，经营分析不只需要查数据库，还需要按统一口径计算下降贡献、找出客户和渠道风险，并将建议绑定到企业制度。

我没有重写 Agent Runtime，而是复用 InsightAgent 的 ReAct Agent、ResourceManager、ToolPack、Text-to-SQL、RAG、HTML 报告和 SSE。我自己完成了 60,000 条可重复合成数据、6 份制度，以及销售诊断、客户流失预警、经销商健康度 3 个确定性 Tool。

真正的工程难点是模型行为不稳定：有时 SQL 可执行但答案抄错数值，有时用间接 Tool 代替目标 Tool，还有只给执行计划却声称报告完成的情况。我对此增加了业务意图路由、ToolPack 顺序门禁、9 类 SQL 错误分类、脱敏 Observation、最多一次纠正、重复 SQL 阻断和确定性事实呈现。综合任务只有在真实出现领域 Tool、知识证据和 HTML 事件后才能完成。

我构建了 30 条冻结 Benchmark，每题新会话，保存 SSE、SQL、Tool、引用和失败原因。Pro 基线是 26/30，修复候选完整运行曾达到 30/30；独立首次发布复验冻结为 28/30，SQL、Tool、RAG 和综合任务仍全部通过。主链路严格九项稳定性从 0/5 到 5/5，迭代后累计 214 项回归测试通过。Week 2 首次 Pro Tool Calling 为 14/40，兼容文本 ReAct 协议后同集复验 38/40。这些数字只代表固定合成集；后一次是查看失败后的修复回归，不夸大为独立盲测或生产准确率。

## 3. 8 分钟讲稿

### 3.1 问题和技术选择

主问题要求 Agent 对华东刹车系统 2026Q2 下降做多维诊断，再检索经销商制度并生成报告。我选 InsightAgent，因为它已有 Data Agent、Text-to-SQL、RAG、Tool Runtime 和报告，如果再做一套通用 Runtime，既增加复杂度，也无法证明业务收益。

### 3.2 业务建模

我建立区域、产品、客户和销售事实 4 张表，固定种子生成 60,000 条数据。异常被植入在华东、刹车系统、2026Q2、经销商渠道，同时保留华南增长作为反例。Gold Truth 不是事后手写百分比，而是从生成数据重新计算并冻结。

### 3.3 Tool 设计

`sales_diagnosis_tool` 负责品类、渠道和利润诊断；`customer_loss_analysis_tool` 负责停止采购或超过阈值的下滑预警；`dealer_health_analysis_tool` 使用销售 40%、活跃度 20%、折扣 20%、毛利 20% 的可解释规则排序。三个 Tool 拆分是为了缩小 Action Space 和错误语义，公共季度、安全除法和数据访问逻辑仍复用。

### 3.4 接入链

HTTP 请求进入 `agentic_data_api.py` 的 `/v1/chat/react-agent`，后端根据数据库和知识库资源识别综合模式。`component_configs.py` 将业务 Tool 注册到 ResourceManager，API 再把所需 Tool 放入受控 ToolPack。ReAct Agent 输出 Action，ToolPack 检查顺序和参数，执行结果成为 Observation 返回 Agent，最终通过 SSE 展示步骤、引用和 HTML。

### 3.5 从 26/30 到 30/30

Day 5 的四个失败分别是：JOIN 别名被预检误拒；SQL 正确但最终金额和百分比抄错；模型通过 `execute_tool/load_tools` 间接调用；综合任务只输出计划却标记完成。我分别修复别名解析、用 Observation 确定性呈现、强制直接领域 Tool、将完成标记绑定到真实事件。

后续又发现四个 SQL 虽执行成功，但 presenter 对结果别名和行/列形状覆盖不足。我增加季度、毛利、渠道贡献和客户下降金额的语义别名映射，并对缺少贡献率列的单行查询拒绝自行计算 100%。定向回归通过后再完整运行 30 题，得到 30/30，而不是把单题重跑结果拼接成总分。

发布时我又按预先承诺只跑一次完整 Pro，结果是 28/30。`v1-dev-sql-05` SQL 正确返回毛利率变化 -2.7839 个百分点，但没有同时呈现 Q1/Q2 两个基准值；`v1-test-sql-07` 返回经销商下降金额正确，但把贡献率分母定义为“所有下降渠道之和”，得到 73.99%，与 Gold 的“区域净下降”口径 74.89% 不同。我冻结结果、不补跑，并把它解释为事实完整性和指标口径契约仍需结构化约束。

### 3.6 稳定性改进

主链路首轮严格全项 0/5，因为最终摘要偶发遗漏时间基准、制度选择不稳定、HTML 超时，以及评测脚本不兼容结构化引用。我改为证据绑定的确定性综合摘要，对经销商制度做定向 `semantic_search`，收紧无效动作和轮数，并兼容结构化引用。修复后重新独立运行 5 次，九项均为 5/5。

## 5. 高频问题与参考回答

### Q1：为什么不直接让模型写 SQL 并做全部计算？

自由 SQL 适合长尾探索，但核心经营口径需要可复现。我保留 Text-to-SQL，同时把销售、客户和经销商的高频口径收敛到参数化 Tool，以减少语义和计算漂移。

### Q2：`@tool` 与普通 Python 函数有什么不同？

业务计算本质仍是 Python 函数，`@tool` 把名称、描述和参数 Schema 转换为 Agent 可发现的 Resource，再由 ResourceManager 注册、ToolPack 挂载和约束执行。

### Q3：ResourceManager 有了 Tool，为什么还要 ToolPack？

ResourceManager 是注册和查找来源；ToolPack 是当次任务可用动作集和执行约束。只注册不代表当前 Agent 已能调用，也不能保证顺序。

### Q4：为什么需要确定性 presenter？

Day 5 证明 SQL Observation 正确后，LLM 仍可能抄错金额或重算错百分比。presenter 对已识别的高风险结果形状从 Observation 直接计算和渲染，模型仍负责解释和建议。

### Q5：为什么只重试一次？

一次能覆盖列名、别名、分组等可纠正错误；更多次会增加延迟、成本和死循环风险。权限和未知错误立即停止。

### Q6：怎样防止重复失败 SQL？

对规范化 SQL 做指纹，保存步骤内已尝试集合。如果纠正后仍是相同 SQL，不再访问数据库。

### Q7：如何判断综合任务真的完成？

不看“已完成”文本，而是看 SSE 轨迹中是否存在目标领域 Tool、有效制度检索和 HTML 输出三类事件。缺任一类就不通过。

### Q8：DeepSeek DSML 是什么问题？

实测中模型偶尔使用特定 DSML 工具调用标记，标准 ReAct 解析器无法识别。我增加兼容解析，但解析后仍必须经过同一 ToolPack 校验，不绕过执行边界。

### Q9：SQL Execution Success 为什么不等于 Answer Accuracy？

SQL 可能查错年份、错口径，也可能查对后被最终答案抄错。所以我分开记录执行成功、事实准确、Tool 选择和引用命中。

### Q10：为什么每题新会话？

避免前题的 SQL、工具和制度内容泄漏到后题，使每条记录的成败更可归因。

### Q11：为什么不只用 LLM-as-a-Judge？

数值、Tool、SQL 和章节可用确定性规则判分；只对建议边界、语义完整性等需要判断的任务做带理由的人工复核，避免引入另一个不可审计模型。

### Q12：26/30 到 30/30 是不是过拟合？

存在风险，所以我保留 Day 5 失败和所有轨迹，不改 Gold，定向测试修复后还要完整重跑 30 题。独立首次发布复验回落到 28/30，反而提供了路径波动和口径契约不足的直接证据；样本仍只有 30 条，所以不声称泛化成绩。

### Q13：为什么不引入 LangGraph？

当前问题集中在 InsightAgent 现有 Tool 选择和恢复链。先在原扩展点内做出可测量改进，比替换编排框架更能控制变量。

### Q14：当前最大技术债是什么？

presenter 仍需要显式覆盖结果形状，Benchmark 规模小，且缺少并发、长时间稳定性和真实流量。下一步应先扩充 challenge set 和结构化中间表达，而不是继续增加新 Agent。

### Q15：如果生产化，你先做什么？

引入真实匿名流量和业务标注，补权限、审计、秘钥管理、资源限制、并发和故障演练，然后再根据失败分布决定是否替换检索或编排模块。

## 6. 失败案例 STAR

**Situation**：Pro 基线中 SQL 已返回正确数值，最终答案却抄错销售额并重算错同比/环比。

**Task**：提高事实准确率，且不把整个 Agent 变成模板报告。

**Action**：保留 LLM 解释，对季度销售、毛利、渠道贡献和客户下降等高风险形状从 Observation 确定性计算，并增加别名/行列形状回归。

**Result**：Answer Fact Accuracy 在修复候选运行由 90% 提升到 100%，独立首次发布复验为 93.33%；说明旧问题已被定向修复，但最终事实字段和指标口径仍需继续结构化。

## 9. Week 1：Text-to-SQL 语义正确性

Day 7 后继续把两个失败抽象为通用能力：用 YAML 管理指标公式、字段/维度和歧义规则，按问题动态注入；对高风险歧义在代码层移除 SQL Tool；用语义预检检查加权公式、时间、Join、范围和去重；建立 18 dev + 8 test + 4 challenge 专项集。

唯一一次 Pro 最终运行是 27/30（90%），SQL 执行、歧义处理和澄清前不查库均为 100%，Day 7 回归 2/2。严格结果集为 76.92%、答案事实为 88.46%，三个公开失败集中在百分比展示、数据覆盖范围和不存在实体处理。详细问答及演示顺序见 `WEEK1_INTERVIEW_GUIDE_DETAILED.md`。

面试重点不是背 27/30，而是说明：为什么 SQL 可执行不等于业务正确，为什么把结果集与答案事实分开，以及为什么最终失败后选择冻结和披露而不是继续刷分。

## 10. Week 4：Agent 失败恢复

Week 4 将各 Tool 的异常收敛到统一分类器和策略层：请求共享一次 retry/replan 预算，
相同失败指纹第二次出现立即断路，最终结果由证据账本输出
`success/failed/partial`。这样可以回答三个工程问题：什么错误值得修、最多修几次、已经
获得的业务事实在后续超时时是否还能安全返回。

Flash 20 题 After 三轮恢复率为 100%、100%、91.67%，有界终止 100%，盲重试与
断路后调用均为 0%；确定性断路专项 20/20。Pro 原始恢复率为 66.67%，轨迹暴露
CLI 风格检索参数、数值字符串和换 Tool 后预算重置。增加无损参数归一、请求级共享
预算与有界自动恢复后，同集回归提升至 91.67%，总通过率从 70% 到 90%，有界终止
保持 100%。必须说明后一次不是独立盲测，并保留 58.33% 等中间失败轮。
