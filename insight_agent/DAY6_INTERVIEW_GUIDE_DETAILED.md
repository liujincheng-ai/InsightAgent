# InsightAgent Day 6 详细面试文档

## 1. 一分钟项目介绍

我在 InsightAgent 上实现了一个汽车配件经营分析 Agent。Day 6 的重点不是增加 Tool，而是把 Day 5 暴露的问题变成可控、可恢复、可审计的执行链。核心改造包括八类 SQL 错误分类、脱敏 Observation、最多一次纠正、成功结果确定性呈现，以及综合任务必须真实完成领域分析、制度检索和 HTML 报告后才能宣告完成。

最终固定 Pro Benchmark 为 30/30，超过 26/30 的正式门槛；Day 5 四个已知失败全部通过。故障集 9/9 分类正确并安全脱敏，可重试错误一次纠正后全部成功。全量测试 139 passed。修复前五次主链路严格结果为 0/5，修复后独立复跑达到 5/5，九个 Rubric 单项均为 5/5。

## 2. 系统调用链

```text
用户问题
  → 识别 SQL / 领域 / 综合任务
  → ToolPack 工作流门禁
  → sql_query 只读预检
       → 数据库错误分类
       → 脱敏 Observation
       → 可重试？最多一次纠正 : 立即停止
  → 成功 Observation / 领域 Tool 结构化结果
  → 知识库真实证据
  → HTML 渲染
  → 确定性 presenter 生成最终摘要
  → SSE 轨迹、引用和 Benchmark 评分
```

## 3. 常见面试题与答案

### Q1：为什么 SQL 重试只能一次？

无限重试会放大模型费用、数据库压力和不可预测行为，而且相同错误通常不会靠重复执行自行消失。一次纠正足以验证 Agent 是否能利用结构化错误反馈；第二次仍失败就应把清晰错误交给用户或上层编排。权限和未知错误连一次都不应自动重试。

### Q2：怎样判断错误是否可重试？

先按 SQLSTATE，再按 PostgreSQL 异常文本和预检错误码分类。语法、表、列、类型/日期、分组、歧义、超时可在约束下纠正；权限拒绝不可由改 SQL 绕过；未知错误缺乏安全修复依据，默认失败关闭。

### Q3：为什么不能把数据库原始异常直接喂给模型？

原始异常可能包含连接 URI、主机、端口、用户名、数据库名、文件路径甚至完整 SQL。Day 6 只暴露稳定错误码、简短提示、是否可重试和剩余预算。这样既降低敏感信息泄露，也减少模型被无关堆栈干扰。

### Q4：如何防止重复失败 SQL？

会话状态记录规范化后的失败 SQL 与错误分类。下一次调用如果 SQL 未发生有效变化，直接消耗剩余预算并返回重复错误，不访问数据库。达到预算后拒绝第三次尝试。

### Q5：SQL 成功为什么答案仍可能错？

LLM 可能在最后一跳抄错数字、单位或重新计算百分比。Day 5 的典型案例把 15,228,822.09 抄成 15,288,822.09。解决方式不是再调 Prompt，而是让 presenter 直接读取成功 Observation，并用 Decimal/数值公式计算环比、同比、毛利变化和贡献率。

### Q6：确定性 presenter 会不会削弱 Agent 灵活性？

它只接管高风险的事实层，不接管问题理解、SQL 生成、Tool 选择或建议生成。结构化数值走确定性路径，自然语言解释仍可由 Agent 完成。这是把概率模型放在擅长的位置，把精确计算交给代码。

### Q7：缺失 ReAct Action 时为何允许恢复？

只允许非常窄的形状：整个输出必须是仅含 `sql` 的 JSON/Python 字面量映射，使用 `json.loads` 或 `ast.literal_eval`，绝不执行任意代码。随后仍进入同一个原生只读 SQL Tool，经过预检、重试预算和审计事件。领域 Tool 恢复也必须能从问题确定性提取完整参数，否则失败关闭。

### Q8：如何防止综合任务“假完成”？

完成条件不读取“已完成”这句话，而读取 ToolPack 状态：必需领域 Tool 是否成功、知识工具是否返回证据、HTML Tool 是否完成。任何一步缺失，`terminate` 不视为终态，最终明确列出缺项，不能生成成功文案。

### Q9：为什么知识库调用过不等于证据正确？

`kb_ls` 或召回另一份制度只能证明调用发生，不能证明回答受目标制度支持。用户明确要求经销商管理制度时，系统检查实际内容是否包含《经销商分级与考核管理制度》，不满足就定向检索 3.2 和 4.2。

### Q10：怎样区分数据事实、规则判断和建议？

数据事实必须来自 SQL/领域 Tool Observation；规则判断必须引用知识库条款；建议可以结合两者，但必须以“建议”标记，不能把推断写成事实。综合摘要固定分为“数据事实、风险判断、制度依据、管理建议”四段。

### Q11：Day 6 怎样从 26/30 提升到 30/30？

首先修复 Day 5 四个已知失败并达到 26/30 门槛。随后对剩余四个 Text-to-SQL 派生事实题逐一定位，发现 SQL 都已成功，失败来自结果别名和形状变化后的 presenter 覆盖不足。扩展毛利率、季度行、渠道贡献和客户下降金额语义后，先定向回归 4/4，再重新执行完整固定集得到 30/30。最终分数来自同一次完整运行，没有拼接选择性结果，也没有修改 Gold。

### Q12：9 类故障如何构造？

语法、表、列、日期/类型、分组和歧义用真实 PostgreSQL 触发；权限和超时使用受控注入，避免破坏实际账号权限或长期占用连接；未知错误验证默认失败关闭。每例同时检查分类、脱敏、尝试次数与最终执行状态。

### Q13：baseline 与 Day 6 怎么公平比较？

使用同一错误样本和同一正确修复 SQL。baseline 在首次失败后停止，因此最终执行成功率为 0；Day 6 对可重试类允许一次纠正，全部成功。非重试类两边都不执行所谓“修复”，避免把绕过权限算成能力。

### Q14：五次稳定性为什么曾是 0/5，最后如何达到 5/5？

严格稳定性要求九项同时成立，修复前 0/5 暴露了摘要漏写时间基准或同比/环比、制度选择漂移、HTML 超时以及结构化引用解析异常。对应修复是：确定性综合摘要、定向制度语义检索、阻断冗余 SQL、减少最大轮数并为恢复留出预算、兼容结构化引用。之后使用相同 Rubric 独立复跑 5 次，最终 5/5，每个单项也都是 5/5。报告同时保留修复前后结果，避免只展示成功样本。

### Q15：如何解释一次 259 秒的任务？

客户端 read timeout 不一定是整个流的绝对墙钟超时；只要流持续返回数据，连接可能继续。Agent 在多轮 SQL、知识与 HTML 步骤中耗尽内部预算后才安全终止。后续应增加端到端 deadline、每阶段预算和取消传播，而不仅是 socket timeout。

### Q16：如何保证评测可审计？

每题独立会话，保存完整 SSE、Tool、SQL、引用、答案与延迟；结果目录拒绝覆盖；固定数据集哈希；失败保留在分母。Git 只提交代码、测试、汇总和文档，原始轨迹与截图留作本地证据，避免把大体积或潜在敏感日志纳入版本库。

### Q17：为什么 Web UI 还要验收？

API 指标不能证明前端把步骤、引用和结果正确展示。Web 验收确认了领域 Tool 和 SQL 的真实步骤、`READ ONLY` 标记、确定性结果表、HTML 完成状态，以及制度 3.2/4.2 在参考来源面板可见。

### Q18：当前最大技术债是什么？

第一，服务端应返回 Token、费用和阶段耗时；第二，仍需引入端到端绝对 deadline、并发与取消传播测试；第三，真实租户权限隔离需要在更接近生产的环境验证；第四，上游 Starlette/Pydantic 弃用警告应随依赖升级处理。

## 5. 面试表达禁区

- 不只说“30/30”，还应说明它来自同一次完整固定集运行；
- 不隐去修复前稳定性 0/5；最终 5/5 是独立复跑结果；
- 不把预警写成客户已经流失；
- 不把 Tool 被调用写成证据必然正确；
- 不估算不存在的 Token 成本；
- 不隐去超时、脚本兼容问题和剩余失败。
