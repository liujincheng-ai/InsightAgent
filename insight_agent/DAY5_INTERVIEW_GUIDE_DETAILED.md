# InsightAgent Day 5 详细面试指南

## 1. 一分钟项目介绍

我实现了一个汽车配件经营分析 Agent。Day 1 到 Day 4 完成了合成业务库、企业制度知识库、Text-to-SQL、RAG，以及销售诊断、客户流失、经销商健康度三个确定性领域 Tool。Day 5 没有继续堆功能，而是建立 30 条固定 Benchmark，把“偶尔跑通的 Demo”变成可复现的工程基线。

这 30 条由 8 条 SQL、6 条 RAG、三个 Tool 各 3 条和 7 条综合任务组成，提前拆成 20 条 dev 与 10 条冻结 test。评测器真实调用 InsightAgent SSE API，为每题创建独立会话，保存完整 Tool、SQL、引用、延迟和最终答案。Flash dev 最终 20/20，Pro 首轮 26/30，冻结 test 10/10。四个失败分别定位为 SQL 执行、事实汇总和 Tool 调用格式问题，而不是用一个模糊总分隐藏。

## 2. 三分钟讲解结构

### 2.1 为什么要做 Benchmark

一次 Demo 成功不能回答三个问题：换一个问法是否还能选对 Tool；SQL 能运行是否真的回答了业务问题；失败时到底是规划、参数、SQL、RAG 还是总结出错。因此我先固定任务、Gold 和评分口径，再执行模型。

### 2.2 如何设计任务

任务覆盖从单能力到组合能力的梯度：

1. SQL 测模型能否生成可执行且语义正确的查询；
2. RAG 测文档、章节和答案是否受证据支持；
3. 三类 Tool 测路由与确定性业务契约；
4. 综合任务测业务事实、制度证据和报告汇总能否协同完成。

我没有把 30 条都用来调试，而是预先分为 20 条 dev 和 10 条 test。test 在 Pro 前冻结，只运行首轮，避免根据 test 答案反复调 Prompt。

### 2.3 如何保证可复现

固定模型、temperature、Prompt 版本、数据版本、Git Commit/dirty 状态和两个数据集 SHA-256。每题新建会话，避免上一题上下文污染。结果目录非空时直接失败，防止覆盖。服务端没有计费 Token 就保留空值，不做伪精确估算。

### 2.4 结果与价值

Pro 首轮 26/30，SQL 成功率 87.5%、事实正确率 90%、预期 Tool 调用率 87.5%、RAG 文档与章节命中率 92.31%、综合任务通过率 85.71%。冻结 test 10/10，但我明确说明样本只有 10 条，不能外推成生产准确率。

四个失败形成了下一天的明确输入：一个 SQL 被预检拒绝，一个 SQL 可执行但汇总事实错误，一个 Tool 用间接入口得到正确数值但违反调用契约，一个综合任务没有执行却声称报告完成。

## 3. 代码调用链

```text
v1_dev.json / v1_test.json
        ↓ schemas.validate_v1_pair
run_eval.py 为每题生成独立 conv_uid 和资源上下文
        ↓ POST /api/v1/chat/react-agent
InsightAgent ReAct Agent → SQL / RAG / 三类领域 Tool / HTML 报告
        ↓ SSE events
parse_events 提取 final、Tool、SQL、引用和成功 Observation
        ↓ metrics.score_record
确定性评分 + manual_reviews.json 人工复核
        ↓
raw/*.json + records.json + summary.json/csv + run_manifest.json
```

关键源码：

- `evaluation/schemas.py`：数据集契约；
- `evaluation/run_eval.py`：真实运行和轨迹保存；
- `evaluation/metrics.py`：确定性评分和分母；
- `evaluation/rescore.py`：不改变原始事件的重新评分；
- `evaluation/apply_manual_reviews.py`：人工评分完整性；
- `tests/insight_agent/test_day5_benchmark.py`：契约和边界测试。

## 4. 数据集设计细节

### 4.1 为什么不是 30 条随机问题

随机问题难以稳定复现，也难确认覆盖是否均衡。我按系统能力分层，并给每类固定配额。这样某类退化时可以明确看到，例如 Pro 的 RAG 是 6/6，而 Text-to-SQL 是 6/8。

### 4.2 Gold Truth 如何产生

数值 Gold 来自参数化只读 SQL、确定性 Tool 输出和既有 Gold 文件；制度 Gold 来自原文文档与章节。模型失败后不能直接修改 Gold。Pro 的区域销售题出现数值冲突时，我重新查询数据库，确认 Gold 的 -3.1685% 和 1.8485% 正确，因此保留模型失败。

### 4.3 每条记录保存什么

必备字段包括 ID、类型、问题、预期事实、Tool、文档、章节、容差、实际答案、实际 Tool、实际 SQL、来源、延迟、模型、pass/fail 和失败原因。除此之外还保存完整 SSE events、会话 ID、评分组件和人工复核理由。

### 4.4 为什么每题新会话

如果复用会话，后题可能从前题继承地区、季度、SQL 结果或制度引用，测试结果就无法归因。独立会话同时避免 RAG 引用追问缓存让后续任务获得不公平优势。

## 5. 指标定义

### 5.1 SQL Execution Success

不是“模型输出了 SQL 字符串”，而是 `sql_query` 后存在成功 Observation。SQL 被预检拒绝、数据库没有执行时记失败。Pro 中 `v1-dev-sql-01` 就说明只保存 `actual_sql` 不足以证明执行成功。

### 5.2 Answer Fact Accuracy

检查关键文字事实和数值是否落在字段级容差内。数值允许合理展示形式，例如 `-0.3268` 与 `-32.68%`，但不会把完全不同的值视为近似正确。

### 5.3 Expected Tool Call Rate

只有轨迹中直接出现预期领域 Tool 才通过。即使 `execute_tool` 间接得到正确数字，也记 Tool 选择失败，因为直接 Tool 契约承担参数约束、可观测性与路由安全责任。

### 5.4 RAG Document Hit Rate

要求实际引用中出现预期文档。不能只因为最终答案提到了文档名就算检索成功。

### 5.5 Citation Section Accuracy

先要求文档命中，再检查章节。文档没有命中时，回答里偶然出现 `4.2` 不能算章节正确。

### 5.6 Integrated Task Pass Rate

组合条件包括 Tool、事实、制度文档、章节、最终报告和无证据编造。任何关键组件失败，综合任务失败。不能让另一个 LLM 给一个不可解释的总分代替组件检查。

## 6. 自动评分和人工复核如何配合

自动评分擅长检查确定字段、数字、Tool 名、SQL Observation 和引用；人工复核负责判断制度是否真的支持结论、风险与事实是否区分、综合报告是否完成以及是否制造因果。

本次 15 条任务需要人工复核。每条都保存 reviewer、decision 和 reason。`v1-dev-integrated-03` 自动和人工都失败：模型只是写了执行计划并触发“已完成”兜底，没有 Tool、制度证据或真实报告。这个案例说明“Agent 说完成”不能当作任务完成。

## 7. 最有价值的故障案例

### 7.1 资源挂载污染评测

Flash run1 把数据库和知识库挂给所有题，纯 SQL 被识别为综合模式，先调用领域 Tool，SQL 通过率受污染。run2 改为所有非综合题只挂单一资源，又导致领域 Tool 没有注册。最终规则是 SQL 仅数据库、RAG 仅知识库、Tool 和综合任务同时挂数据库与知识库。

结论：评测环境不是中性的。资源、Prompt、模型和路由配置都属于被测版本，必须记录。

### 7.2 SQL 可执行但答案错误

`v1-dev-sql-02` 的 SQL 成功执行，但最终答案把正确 Gold 的环比 -3.17%、同比 +1.85% 写成 -2.79%、+2.25%。如果只统计 Execution Accuracy，这条会被误记为成功。

结论：至少分开 SQL 执行成功和答案事实正确。

### 7.3 数值正确但 Tool 选择失败

`v1-dev-sales-02` 返回了正确的华南销售额和环比，却使用 `execute_tool`/`load_tools`，没有直接调用 `sales_diagnosis_tool`。

结论：最终数字正确不能替代过程契约。生产系统中间接入口可能绕过参数和审计约束。

### 7.4 虚假完成

`v1-dev-integrated-03` 没有真实 Tool 或制度证据，却输出“已完成 HTML 报告”。

结论：终止条件应检查必要 Observation 是否存在，不能只检查模型是否输出完成措辞。

### 7.5 判分器也会有缺陷

首轮自动评分把正确的 `30 日` 因空格差异误判。修复为中文空白归一化后，从冻结 events 重新评分，未重新请求模型。

结论：评测器本身也需要测试、版本号和变更记录；重新评分不能改原始轨迹。

## 8. 高频面试题与参考回答

### Q1：为什么 SQL 执行成功率不等于答案准确率？

合法 SQL 仍可能使用错误时间范围、JOIN、过滤或聚合；即使数据库结果正确，模型在最终汇总时也可能抄错。我的 Pro 中就有一条 SQL 执行成功但环比、同比都写错，所以分开统计 87.5% 的执行成功率和 90% 的任务级事实准确率。

### Q2：为什么要拆 dev 和 test？

dev 用于发现题面、资源配置和评测器问题，test 在模型运行前冻结。否则根据测试失败不断改 Prompt 或 Gold，最终指标只是对测试集过拟合。本项目的 test 10 条未参与 Flash 调试，只做一次 Pro 首轮。

### Q3：test 10/10 是否说明系统准确率 100%？

不能。样本太小且是合成业务场景，只说明这 10 条冻结任务在该模型、Prompt、数据和 Commit 状态下通过。报告明确不宣称统计代表性。

### Q4：为什么保留完整轨迹？

最终答案错误只告诉我结果不对。轨迹才能区分是 SQL 被预检拒绝、Tool 没调用、参数错误、RAG 未命中，还是最后汇总抄错。四个 Pro 失败依赖轨迹才能准确分类。

### Q5：为什么不直接用 LLM-as-a-Judge？

V1 的关键事实、Tool、SQL 和章节大多可确定性判断，先用明确规则能减少主观性。需要判断证据支持和业务边界时再人工复核，并保存理由。未来可以引入 LLM Judge，但仍需用人工标注集校准一致性。

### Q6：人工评分怎样避免随意？

先定义 rubric：检查事实、来源、结论边界和报告完成情况；每条保存 reviewer、decision、reason；不能只有总分。人工失败还必须能指向原始 Tool/引用/答案证据。

### Q7：如何防止 test 泄漏？

运行前冻结文件和 SHA-256；Flash 只跑 dev；Pro test 只运行首轮；结果目录拒绝覆盖；失败后不改 Gold、不选择性重跑。若系统修复，需要生成新的结果目录和版本，而不是覆盖本轮。

### Q8：数值容差怎样设置？

容差按字段定义，金额通常允许分币级误差，百分比允许展示精度差异，同时显式接受小数率和百分比形式。容差不能大到掩盖业务错误，例如 -3.17% 与 -2.79% 不应视为同一答案。

### Q9：为什么 Tool 任务还要挂知识库？

这是当前 InsightAgent 二次开发路由的真实约束：数据库加知识库会进入 InsightAgent 综合模式并注册三个领域 Tool；只挂数据库走通用 SQL 路径。评测器必须按当前产品入口复现真实资源组合，同时在 manifest 中记录，后续可以再优化注册逻辑。

### Q10：为什么 RAG 文档命中和章节准确要分开？

命中文档只说明大方向对，长文档中仍可能引用错误章节。先判文档，再判章节，避免回答里偶然出现 `4.2` 就被认为检索正确。

### Q11：为什么不能根据模型失败修改 Gold？

那会把模型答案变成标准答案，评测失去意义。出现冲突时必须回到数据库或制度原文独立复核。本次 SQL 冲突用只读查询确认 Gold 正确，因此保留模型失败。

### Q12：结果目录为什么禁止覆盖？

覆盖会丢失第一次失败和调试过程，无法证明 test 是首轮。新运行必须使用新目录，manifest 记录模型、参数、数据哈希和 Git 状态。

### Q13：为什么没有成本指标？

当前 SSE API 没有返回可审计的计费 Token。上下文占用不等于计费 Token，我选择保留 `null` 并写明原因，而不是根据公开价格和不完整数据制造精确成本。

### Q14：怎么处理单题超时？

每题有独立超时和异常捕获；超时记为该题失败并保留错误，后续题继续。不能因为一题挂死整个 30 条运行，也不能把超时题从分母删除。

### Q15：如果中途进程退出怎么办？

当前实现每题结束立即写 raw 文件，因此已完成任务仍保留。V2 可增加 manifest 状态和显式 resume，但 resume 必须识别已完成 ID，并把恢复运行标成新版本，不能伪装成无中断首轮。

### Q16：如何证明没有只测本地 Python 函数？

评测器 POST 到正在运行的 `/api/v1/chat/react-agent`，消费真实 SSE，记录真实会话 ID、ReAct step、Tool、SQL 和 citations。单元测试只验证评测器契约，冻结结果来自真实 Flash/Pro 服务。

### Q17：为什么综合任务通过率低于 RAG？

综合任务要求同时满足更多组件：领域 Tool、事实、制度、章节和报告终止。任意一步失败都会失败。纯 RAG 只有检索与回答链路，因此组合可靠性通常更低。

### Q18：你的失败分类有什么用？

它把优化方向变成可执行任务。SQL 预检拒绝进入 Day 6 的错误分类与有限重试；汇总错误需要结构化结果约束；间接 Tool 调用需要路由/解析修复；虚假完成需要基于 Observation 的终止检查。

### Q19：为什么 Flash 20/20，而 Pro 只有 26/30？

Flash 运行的是 dev，并且是资源矩阵修正后的调试结果；Pro 是另一个模型的独立首轮，且覆盖冻结 test。模型更“强”不保证特定 ReAct 格式更稳定，Pro 的失败主要是 SQL 汇总和 Tool 调用格式。这也是必须按模型分别冻结基线的原因。

### Q20：如果要扩展到生产，下一步补什么？

先扩大并分层数据集，引入真实脱敏业务标签、多轮与负向用例；增加并发、权限和长时间稳定性测试；为 Token/成本建立服务端可审计记录；对人工评分做双人一致性；对 Prompt、Tool、数据和评测器建立正式版本管理。

## 9. 面试现场可展示的证据顺序

1. 展示 `v1_dev.json` 和 `v1_test.json` 的类型与 Gold；
2. 展示 `schemas.py` 的 20/10、类型配额和重复检查；
3. 展示 `run_eval.py` 的独立会话、资源矩阵、SSE 保存和目录防覆盖；
4. 展示 `metrics.py` 中 SQL Observation 与 Tool/RAG 组件判分；
5. 展示 Pro `run_manifest.json` 和 `summary.json`；
6. 打开四个失败的 raw JSON，解释定位链路；
7. 展示 `manual_reviews.json`，说明人工判断不是黑盒总分；
8. 最后展示 101 passed 与 Ruff 结果。

## 11. 最终复盘

Day 5 最大的工程价值不是得到一个 86.67% 数字，而是把结果拆成可解释的组件，并让每个失败都能回到原始 Agent 轨迹。评测也暴露了自身缺陷：资源组合会改变路由，空白差异会造成误判，SQL 文本存在不等于执行成功。通过版本化数据、不可覆盖目录、重新评分记录和人工理由，最终形成了一个诚实、可复核、能驱动 Day 6 修复的基线。
