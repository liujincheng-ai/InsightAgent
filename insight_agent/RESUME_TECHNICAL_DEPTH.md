# InsightAgent 项目简历技术深度与面试证据

> 本文对应各岗位最新版项目简历。目标是保证简历中的每个技术要点都能解释问题、方案、实现、验证和限制，并能定位到实际源码。

## 1. 项目问题与架构主线

业务问题是：“华东刹车系统第二季度为什么下降，哪些渠道和客户影响最大，企业制度允许采取什么措施？”

单纯 Text-to-SQL 只能返回表格，单纯 RAG 只能返回制度；业务回答还要求指标口径一致、步骤完整、失败可终止。因此系统将一次综合任务拆成：

```text
自然语言问题
→ 意图与高风险歧义判断
→ SQL / 确定性领域 Tool 获取经营事实
→ 企业制度检索
→ 证据绑定与 HTML 报告
→ SSE 输出完整轨迹
```

系统由 ReAct 执行循环、SQL/RAG Tool、三个领域 Tool、ToolPack 门禁、业务语义层、确定性事实呈现和评测体系组成，前后端通过 SSE 传递执行步骤与最终结果。

## 2. Agent 执行编排：为什么需要完成契约

### 问题

仅在 Prompt 中要求“先查数据、再找制度、最后生成报告”，模型仍可能直接检索制度、跳过领域分析或提前结束。输出形式看似完整，过程却没有形成数据证据。

### 方案与实现

`SalesDiagnosisFirstToolPack` 在 `ToolPack` 中维护三个阶段状态：

| 当前状态 | 允许的下一步 | 越级行为 |
|---|---|---|
| 未完成领域分析 | Planning、指定领域 Tool | 返回缺少领域分析 |
| 已有领域结果 | Planning、知识检索 | 限制报告生成 |
| 已有知识证据 | Planning、知识检索、HTML | 允许生成报告 |
| 前置条件缺失 | 不允许 terminate 完成 | 继续返回缺失步骤 |

领域 Tool 根据问题选择最窄职责：销售下滑走 `sales_diagnosis_tool`，客户风险走 `customer_loss_analysis_tool`，经销商风险走 `dealer_health_analysis_tool`。这样保留 Agent 对自然语言的适应能力，同时把综合任务的必要步骤落实到执行层。

### 取舍

采用 ReAct 循环、资源管理和 SSE 组成统一运行链路，并将顺序约束集中在 ToolPack，避免多套 Runtime 之间的状态同步问题。

### 限制

当前阶段状态在 Tool 调用返回后更新，尚未对每一种结果建立统一的 `success/error/partial` 完成合同。工具若正常返回错误对象，仍可能被标记为完成。因此不能把它描述成生产级任务状态机、持久化队列或断点恢复系统。

## 3. 会话记忆与上下文管理：不只是保存聊天记录

### 问题

长链 ReAct 任务会连续产生 Thought、Action、Observation、任务计划和引用。只把聊天文本回填 Prompt，会造成 Tool 大结果持续挤占上下文；只保留当前轮次，又会让 Agent 忘记已经完成的步骤、重复检索或重复执行 SQL。因此记忆系统需要同时解决“保存什么、如何按会话隔离、上下文超限时丢弃什么、前端如何感知”四个问题。

### 记忆模型与数据流

| 层级 | 实现 | 作用 |
|---|---|---|
| 消息记忆 | `MetaDbGptsMessageMemory` | 按 `conv_id` 保存 Agent 多轮消息 |
| 计划记忆 | `DefaultGptsPlansMemory` | 记录任务拆解与执行进度，避免已完成步骤丢失 |
| 展示历史 | `StorageConversation` + v2 JSON | 持久化最终内容、步骤、任务计划、引用、子 Agent 与安全化输入文件元数据 |
| 运行时记忆 | `REACT_AGENT_MEMORY_CACHE[conv_id]` | 同一进程内复用 `GptsMemory`，避免每轮重新创建状态容器 |
| 上下文预算 | `ContextManager` | 统计 Token，按阈值压缩历史并以 SSE 输出 `context.status` |

```text
conv_id
├─ Message Memory：用户消息 / Agent 消息
├─ Plan Memory：任务与完成进度
├─ Structured History：steps / task_plan / citations / final_content
└─ Context Budget：NORMAL → WARNING → ERROR → 超限回退
```

在 WARNING 阶段，系统先截断过旧的 Tool Observation，再裁剪旧 ReAct 轮次，同时保留近期轮次和 `task_progress`；更高压力下可使用结构化摘要，若模型仍返回 context-too-long，则走紧急裁剪。每次预算状态和实际压缩层级都通过 SSE 发给前端。对于“把刚才引用的制度来源列出来”这类追问，系统直接从已持久化的结构化引用生成答案，不再重复执行检索和规划链。

### 边界

当前实现是**会话级任务记忆**，不是跨会话用户画像、向量化情景记忆或自主反思型长期记忆。内存缓存用于同进程复用，持久化消息和展示历史承担可追溯记录；现有验收尚未覆盖服务重启后的任务续跑、分布式多实例一致性及所有超长上下文压缩分支，因此简历不写“生产级长期记忆”或“断点恢复”。

## 4. 领域 Tool：为什么不用一个万能分析函数

三个业务问题的输入、输出和失败语义不同：

| Tool | 输入重点 | 确定性输出 |
|---|---|---|
| 销售诊断 | 区域、品类、季度 | 同比/环比、毛利、产品和渠道贡献 |
| 客户风险 | 区域、品类、周期、阈值 | 基准期/当期销售、下降金额、客户等级 |
| 经销商健康 | 区域、季度、Top-N | 销售、活跃、折扣、毛利扣分与风险等级 |

拆分后 Tool description 更集中，参数可以独立校验，失败定位也更直接。共同指标下沉到共享计算模块，避免三个 Tool 各自实现一套公式。

这里的“客户流失”是交易行为预警，不是经过人工确认的流失标签；经销商健康度是可解释规则，没有真实监督学习标签。面试时应主动说清这个边界。

## 5. Text-to-SQL 语义层：SQL 能执行为什么仍会错

### 错误类型

- “销量”误用销售额或行数；
- 环比/同比周期边界错误；
- Join 后重复计算客户；
- 对行毛利率做简单平均；
- 贡献率使用错误分母；
- “区域”未区分交易发生区域和客户所属区域；
- 无数据、真实零值与超出数据范围混在一起。

### 三层处理

**语义上下文。** `business_glossary.yaml` 维护指标公式、单位、同义词、Schema 含义、时间范围和歧义规则；`semantic/layer.py` 根据当前问题选择相关项，减少全量 Prompt 噪声。

**数据库视图。** `insight_quarterly_sales` 按季度、交易区域、品类和渠道聚合销量、销售额、毛利与加权毛利率；`insight_quarterly_customer_sales` 在同一交易区域口径上增加客户粒度，用于跨期比较。两个视图都是交易区域口径，当前没有客户所属区域专用视图。

**执行前预检。** 检查问题中的区域、品类、渠道是否保留，比较周期是否完整，销量是否使用 `SUM(quantity)`，客户数是否去重，加权指标是否使用正确分子与分母。预检是规则式防线，当前尚未使用 SQL AST 做完整语义分析。

### 高风险歧义

“哪个区域最好”缺少指标和时间，查询任何数据都会暗中选择口径。系统将澄清问题写入运行状态，当前 ToolPack 只提供终止能力，使本轮无法先查库再倒推用户意图。低风险展示问题不需要反复澄清。

## 6. 具体排障：渠道贡献率 73.99% 与 74.89%

### 现象

Day 7 最终复验中，经销商渠道及下降金额 395,312.25 元正确，贡献率却是 73.99%。SQL 成功执行，因此语法和连接层面没有报错。

### 定位

实际 SQL 以“所有下降渠道下降额之和”作为分母，排除了增长渠道；Gold 口径要求同一范围所有渠道的基准期总额减当期总额。增长渠道会抵消一部分下降，两种分母因此产生不同结果。

### 公式

```text
分项下降金额 = 分项基准期销售额 − 分项当期销售额
范围净下降 = 范围基准期总销售额 − 范围当期总销售额
分项下降贡献率 = 分项下降金额 / 范围净下降
```

范围必须同时保留区域、品类和两个比较周期。不能用 Top-N 行或仅负向渠道的局部和代替范围总额。

### 修改

- 在业务词典中固定净下降分母；
- 预检要求贡献率查询包含范围级总量；
- 当渠道 Observation 含完整结果时，由确定性呈现重新计算分母；
- 毛利率回答同时绑定 Q1、Q2 和百分点变化，避免只返回差值。

### 验证

Week 1 Pro 最终运行中，贡献率题返回 74.89%，毛利率题返回 Q1 28.91%、Q2 26.13%、变化 −2.78 个百分点，两个 Day 7 回归案例均通过。该结论仅覆盖冻结问法与这次模型运行。

## 7. SQL 失败恢复与安全

### 错误分类

应用层把常见失败区分为语法、表不存在、列不存在、类型/日期、分组、列歧义、权限、超时和未知错误。Observation 返回可供模型纠正的信息，同时避免输出连接串、密码或完整数据库异常。

### 有限恢复

- 多条 SELECT 属于输出形状错误，在数据库执行前阻断，可允许一次纠正；
- 相同 SQL 再次失败时停止，避免循环消耗；
- DML、DDL 和只读权限违规不可重试；
- 领域 Tool 使用参数化 SQL；
- 数据库账号 `insight_readonly` 提供最终写权限边界。

Prompt 负责说明行为，应用层负责预检与重试边界，数据库权限负责最终拒绝写操作。三层职责不同，不能用 Prompt 代替权限控制。

## 8. RAG 与证据链

六份制度文档带稳定章节号，覆盖经营目标、经销商管理、客户预警、价格折扣、库存补货和质量售后。综合任务要求先取得经营事实，再检索制度，最后组织建议。

数据事实必须来自 SQL 或领域 Tool Observation；制度判断需要文档与章节；经营建议可以由模型组织，但不能把相关性写成唯一因果。知识链路使用 ChromaDB、中文 Embedding、文档切块和语义检索，并通过稳定章节号保留引用来源。

## 9. 评测设计与数字边界

### V1 综合集

固定 20 dev + 10 test，覆盖 Text-to-SQL、制度 RAG、三个领域 Tool和综合任务。DeepSeek Pro 同一题集基线为 26/30，首次独立发布复验为 28/30；7 道综合任务在该次复验中通过。Day 6 曾出现 30/30 修复候选，但没有用峰值替代独立复验。

### Week 1 语义集

18 dev + 8 test + 4 challenge，覆盖时间、Join、销售额/销量、加权指标、贡献、无数据和歧义。Pro 最终规则式自动评分为 27/30，并保留三个失败：

1. 加权折扣率返回小数比例，但答案没有明确转成百分数；
2. 2027 Q1 聚合返回 0，却没有说明数据截止到 2026-06-30；
3. “不存在品类”被误解为产品维表的孤儿记录。

### 当前评分器限制

- SQL 执行状态根据 Observation 文本和错误标记推断；
- 结果表按行内值匹配，未完整绑定列名语义；
- 答案事实使用数值和字符串包含判断，不能完整理解主体关系和否定；
- 比例与百分数归一化缺少显式单位类型；
- 题集规模小且包含开发期可见的 dev 题。

因此简历写“固定合成集上的自动评分为 27/30”，不写“Text-to-SQL 准确率 90%”。这些限制本身也是后续改进评测器的明确需求。

## 10. Week 2 Tool Calling 结果与失败解释

Week 2 使用 40 题冻结集区分模型自主选择和生产规则兜底。评测模式只暴露三个业务 Tool、`sql_query` 和 `terminate`，关闭规则预选、首调用门禁和漏调恢复；生产模式保留这些机制。

Flash 对三种配置各运行三次。`baseline` 的选择与参数有效率均值为 98.33%；`positive` 均为 93.33%；`boundary` 选择为 93.33%、参数有效率为 94.17%。`boundary` 的三个业务 Tool 聚合召回率均高于 92%，多余调用率为 0.72%，但参数有效率未达到 95% 门槛。结果说明完整 Schema 能提供执行前防线，却没有在这组运行中提高模型端指标。

首次 Pro `boundary` 运行通过 14/40，选择准确率 40%。24 条选择失败中，23 条没有形成可执行 Action；模型输出常见为一行式、JSON、蛇形字段或全角冒号 ReAct，而原解析器只接受窄格式文本。兼容明确 Action 的结构化表达、同时拒绝猜测裸业务参数后，同一冻结集复验为 38/40，选择 97.5%、参数有效率 100%，三个业务 Tool 召回率均为 100%。生产烟测仍为 3/3。

面试时需要主动说明：Week 2 已达到预登记工程门槛，但复验发生在查看首次失败之后，并使用同一冻结集，因此不是独立盲测；不能隐藏 14/40，也不能把 38/40 或生产 3/3 扩大为生产准确率。

## 11. Week 4：失败恢复与稳定性

Week 4 不再让每个 Tool 各自解释异常，而是把失败归一成参数错误、SQL 可修复、无数据、
RAG 空召回、权限拒绝、Tool 异常、超时、流程阻断和未知错误。请求级策略只有一次恢复
预算；相同规范化失败连续出现两次即断路；最终状态由已验证证据决定为
`success/failed/partial`，请求超时也会保留已完成阶段。

冻结集为 12 dev + 6 test + 2 challenge。Flash After 三轮恢复率为
100%/100%/91.67%，有界终止均为 100%，不可恢复错误盲重试与断路后调用均为 0%；
平均延迟由 Before 47.36 秒降至 35.66 秒。20 次确定性断路器专项均在第二次相同失败
打开断路。Pro 原始轮恢复率为 66.67%、总通过率 70%；轨迹归因到 CLI 风格知识检索
参数、数值字符串、跨 Tool 预算重置和首次检索绕过。增加无损参数归一、请求级共享预算、
隔离故障的一次有界自动恢复和首 Tool 证据门禁后，同一冻结集 Pro 恢复率达到 91.67%、
总通过率 90%，有界终止 100%，盲重试和断路后调用均为 0%。

这组结果说明应用层安全边界可稳定执行，但模型恢复质量仍有差异；20 题合成故障、
单机环境和隔离注入不能外推为生产 SLO。

## 13. 两分钟面试讲法

> 我构建了一个面向企业经营分析的 InsightAgent，将销售数据、指标计算和企业制度放到同一条分析链路里。项目中的核心难点是模型会跳过工具、SQL 能执行但口径错误，以及最终答案漏掉查询事实。
>
> 我设计了“领域分析、制度检索、报告生成”三阶段门禁；同时按会话组织 Message/Plan Memory 和结构化历史，用 Token 预算分层压缩旧 Observation 与历史轮次，并把上下文状态通过 SSE 暴露给前端。随后把同比、毛利率、贡献率等稳定逻辑拆成三个参数化 SQL Tool，再用 YAML 业务词典、只读 View 和 SQL 预检约束 Text-to-SQL。一个具体问题是渠道贡献率被算成 73.99%，我通过 SQL 和 Gold 对比确认分母只包含下降渠道，随后改成范围整体净下降口径，回归结果为 74.89%。
>
> 为了避免只讲 Demo，我写了真实 SSE 评测器，保存每题 SQL、工具、Observation 和失败。V1 同一 30 题 Pro 从 26/30 到首次独立复验 28/30，语义专项集最终自动评分 27/30，同时保留三个失败。我能说明这些指标的判分方式和局限，也能定位每项改动对应的源码。
>
