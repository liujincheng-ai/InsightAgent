# Week 4 面试指南：Agent 失败恢复与稳定性

## 1. 一分钟讲法

我为 InsightAgent 增加了统一失败恢复层。核心不是在 Prompt 里写“请重试”，而是把
Tool 结果分类为 SQL 可修复、无数据、RAG 空召回、参数错误、权限、异常、超时和工作流
阻断，并在 ToolPack 层给出一次 Retry/Replan 预算。相同 Tool、规范化参数和错误连续
两次失败会打开断路器；已有成功 Observation 时，后续失败返回 partial，明确已完成、
未完成、原因和下一步。

我冻结了 20 条故障集，用 Flash 对 Before/After 各跑三次。After 平均通过率从 51.67%
提升到 96.67%，恢复率 97.22%，有界终止 100%，权限等不可恢复故障盲重试从 33.33%
降到 0%，平均延迟下降 11.70 秒。Pro 原始运行恢复率只有 66.67%；后续按用户要求做
通用协议与状态机优化，同集回归达到 91.67%，总通过率从 70% 提升到 90%，有界终止
保持 100%。原始与中间失败轮仍全部保留。

## 2. 为什么错误对象最危险

很多 Tool 不会抛异常，而是正常返回 `{"status":"error"}`、空列表或无证据文本。
如果 Runtime 只看 Python 调用是否返回，就会把失败步骤标为完成，继续生成看似完整的
报告。Week 4 的分类器同时检查异常、Mapping、JSON 字符串和常见状态字段，再把成功
与证据存在性分开。

## 3. Retry 和 Replan 的区别

- Retry：目标 Tool 和任务不变，但根据结构化错误修正 SQL 或参数；最多一次。
- Replan：当前查询路径没有进展，需要换范围、检索方式或合适 Tool；最多一次。
- Terminate：权限、未知错误、预算耗尽、断路器或请求级超时，立即结束。

把无数据当 Retry 会原样重复；把权限拒绝当 Replan 可能绕过安全边界，因此动作必须由
失败类型决定，而不是让模型自由解释。

## 4. 指纹和断路器如何实现

指纹包含 Tool 名、递归排序后的参数和失败类型。SQL 会统一大小写、空白和末尾分号，
避免格式变化逃逸。连续成功会重置计数；连续第二次相同失败打开断路器并把决策覆盖为
Terminate。20 次独立专项试验均在第二次触发，断路后调用为 0。

## 5. partial 为什么不是失败文案

partial 是状态合同，不是一句“部分完成”。Tracker 只把成功且有证据的业务 Tool 计入
已完成；`todowrite` 和 `terminate` 不计入。最终结果必须列出：

1. 已完成的可验证步骤；
2. 未完成的具体 Tool/阶段；
3. 结构化失败类型和安全原因；
4. 只重试未完成步骤的下一步。

如果数据库事实成功、制度检索失败，系统可以保留销售额和同比/环比，但不能凭常识补写
制度建议。

## 6. 最有价值的排障案例

首次正式候选出现 1127 秒单例，超过声明的 120 秒上限。根因不是 Agent 策略，而是本地
OpenAI 兼容桥在 `async` 路由内调用同步 `urllib.urlopen`；慢请求锁住整个事件循环，取消
信号无法传递，后续 case 也被串联污染。我改为 `httpx.AsyncClient` 异步流式转发，保留
candidate1 六轮，再将 Before/After 整套重跑为 candidate2。120 个 case-run 最大 120.12
秒，没有超过 121 秒。

## 7. 为什么 Flash 通过而 Pro 原始轮未通过

故障恢复不仅依赖分类器，还依赖模型在收到 `retry/replan` 后是否生成正确下一动作。Pro
更常生成 CLI 风格知识检索参数、数字字符串或换 Tool，原控制层没有吸收这些协议差异，
原始恢复率为 66.67%。用户后续明确要求优化后，无损参数归一、共享预算和有界恢复将
同集结果提升到 91.67%；它是同集修复回归，不是独立盲测。

## 8. 主 Demo 如何从 0/3 到 3/3

第一次三轮都在 120 秒超时，因为领域数据和制度证据已经齐备，模型仍继续写代码或等待
额外轮次。将生产集成上限从 8 收紧到 5 后，证据齐备即进入确定性 HTML fallback，核心
业务项 3/3，但一轮模型跳过 `todowrite`。最后把固有三阶段计划在启动时确定性写入 SSE
和历史，最终严格九项 3/3，平均 74.29 秒。

## 9. 面试官追问：是不是规则太多，不像 Agent

回答：模型仍负责理解自然语言、生成 SQL、选择检索 Query 和组织表达；规则只控制不可
协商的安全与完成边界。企业 Agent 的价值不是最大化自由度，而是在可追溯成本下让模型
在明确边界内工作。评测模式仍保留模型自主行为，生产模式加入门禁和确定性 fallback，
两类结果分开报告。

## 10. 不能夸大的地方

- 20 条合成故障集不是生产分布。
- 断路器专项是确定性组件验收，真实模型基准没有强迫同参重复。
- Pro 原始恢复率未达标；优化后同集回归通过，但独立 holdout 尚未验证。
- 当前没有完整 RBAC、Document ACL、多租户、高可用和审计后台。
- 本地 Embedding 不代表远程 LLM 推理完全离线。
