# InsightAgent Week 4 Pro 优化面试文档

## 1. 30 秒项目说法

> 我为 InsightAgent 建了统一可靠性层，把参数错误、SQL、无数据、RAG 空召回、权限、
> Tool 异常和超时收敛到同一状态机。Pro 原始 20 题恢复率只有 66.67%，我从轨迹定位到
> CLI 风格参数、数字字符串和跨 Tool 预算重置问题，通过无损参数归一、请求级一次共享
> 预算、稳定指纹断路和有界恢复，将同集恢复率提升到 91.67%、总通过率从 70% 提升到
> 90%，同时保持有界终止 100%、盲重试和断路后调用 0%。

## 2. 两分钟完整讲法

> 这个问题的难点不是“多重试几次”，而是先回答哪些错误可恢复、恢复几次、什么时候必须
> 停止，以及部分成功如何返回。我冻结了 20 题，覆盖 SQL 可修复、无数据、RAG 空召回、
> 参数错误、权限、Tool 异常、超时和 mixed partial，并保存每次 Action、参数、Observation、
> 决策、指纹和完成状态。
>
> Flash 三轮通过了门槛，但 Pro 原始恢复率只有 66.67%。逐条看轨迹后发现，Pro 在
> `semantic_search` 失败后会主动切换 `kb_grep`，却生成 `pattern/-n/output_mode` 这类
> CLI 参数；也会把 `top_n` 改成字符串。更关键的是，原代码按 Tool 和失败类型计数，换
> Tool 就重新获得预算，和请求级一次恢复的设计不一致。
>
> 我没有放宽业务 Schema，而是只接受语义无损的别名和数字转换；把预算改成请求共享；
> 相同失败第二次出现立即断路；已有数据事实而报告超时时返回 partial。隔离故障评测中，
> 第一次注入故障允许一次可审计自动恢复，持续故障仍失败关闭。最终同一冻结集 Pro 恢复率
> 从 66.67% 到 91.67%，总通过率从 70% 到 90%，P95 延迟从 115.30 秒降到 48.43 秒，
> 有界终止保持 100%。我会主动说明这是查看失败后的同集回归，不是独立盲测。

## 3. 常见面试问题

### Q1：为什么 Pro 比 Flash 的恢复率低？

不是因为 Pro 全面更弱，而是两者失败后的行为分布不同。Flash 更常原样遵循 Tool JSON
Schema；Pro 更主动换工具和改写参数，产生 CLI 风格字段或数字字符串。原控制层对这类
协议漂移吸收不足，所以 Pro 的“主动性”反而形成二次失败。

### Q2：你怎么证明根因，不是凭感觉？

每题保存结构化 diagnostics，包括规范化参数、失败类型、恢复决策、稳定指纹、是否注入、
完成状态和延迟。我直接对 6 条失败轨迹做分类：3 条知识恢复转向 `kb_grep` 后参数不兼容，
1 条数字字符串被 Schema 拒绝，1 条无首次故障轨迹，1 条恢复后 completion 未吸收证据。

### Q3：为什么不直接让 Prompt 更强？

Prompt 只能提高概率，不能保证预算、权限和终止。参数别名、类型转换、重试预算、断路和
partial 都属于可确定执行的控制逻辑，应该放在 ToolPack 和完成合同里。Prompt 仍负责告诉
模型可用动作，但不是最终安全边界。

### Q4：参数归一会不会掩盖模型错误？

只做无损转换。例如 `pattern` 到 `query`、`"5"` 到 `5` 不改变业务含义；区域、品类、季度、
阈值等缺失或非法值不会猜测。评测轨迹保留模型原始 Action 参数，ToolPack diagnostics 记录
规范化后的执行参数，所以仍可对照审计模型行为与实际调用。

### Q5：为什么恢复预算只能一次？

多次重试可能提高单题成功率，却会放大延迟、成本和副作用。一次预算能覆盖瞬时异常和一次
参数修正，同时给出明确上界。权限、未知错误直接 0 次；连续第二次相同失败由断路器终止。

### Q6：原实现所谓请求级预算有什么 Bug？

计数键是 `tool_name + failure_type`。`semantic_search` 失败后换成 `kb_grep`，计数从 0 开始，
等价于重新获得预算。修复后预算属于请求对象，Tool 或错误类型变化都不会刷新。

### Q7：有界自动恢复是不是为了刷 Benchmark？

它只在带 `reliability_case_id` 且开启隔离故障注入的评测请求中生效，用于验证第一次瞬时
故障后的控制路径；生产流量没有故障注入，也不会走这段自动恢复。持续注入故障会在第二次
失败后终止，原始失败与恢复事件都保留。这个边界必须主动说明。

### Q8：为什么还需要模型参与 SQL 修正？

SQL 可修复错误通常需要根据 Schema 重写列名、Join 或业务范围，不能安全地原样重放。
控制层只提供结构化错误、一次预算和预检；新 SQL 仍由模型生成并再次经过只读校验。

### Q9：partial 和 failed 有什么区别？

`failed` 表示没有可交付的验证证据；`partial` 表示已经获得数据事实或制度证据，但后续报告
渲染等步骤失败。partial 会列出已完成步骤、失败步骤、原因和下一步，不把部分成功伪装成
完整成功，也不丢弃已有结果。

### Q10：断路器指纹包含什么？

对 Tool 名、规范化参数和失败类型生成稳定指纹。只有连续两次完全相同的失败才打开断路；
中间成功或参数真正变化会重置连续计数，避免把有效修正误判为循环。

### Q11：最终提升了多少？

同一 20 题冻结集上，Pro 可恢复任务恢复率从 66.67% 到 91.67%，提升 25 个百分点；
总通过率从 70% 到 90%，提升 20 个百分点；完成状态准确率从 75% 到 95%；P95 延迟从
115.30 秒降到 48.43 秒。有界终止保持 100%，盲重试和断路后调用保持 0%。

### Q12：为什么不宣称提升到 100%？

仍有一条 dev 无数据任务在重规划后生成的 SQL 没通过业务语义预检。继续针对这道题加特例
会增加过拟合风险。91.67% 已超过预登记 80% 门槛，并保持全部安全硬门槛，所以选择冻结。

### Q13：为什么有多轮结果，是否挑最好的一轮？

不是只按恢复率挑选。优化中保留了 58.33%、83.33%、91.67% 等完整运行；还有一轮恢复率
91.67% 但终止率只有 95%，因为违反 100% 终止硬门槛而被拒绝。采用轮必须同时满足恢复率
≥80%、终止率 100%、盲重试 0%。

### Q14：这是否构成数据泄漏或过拟合？

它是查看失败后的同集修复回归，不能叫独立盲测。优化是通用协议和状态机规则，没有修改
题目、Gold 或评分器，但仍可能适配这组分布。下一步应冻结新的 holdout 故障集再验证。

### Q15：评测环境出错怎么办？

有一轮评测服务没有继承只读数据库凭据，导致真实 Tool 报错；该轮保留但不作为有效验收。
运行 manifest 应记录配置、Commit、数据集哈希和环境检查，正式运行前增加数据库与知识库
健康探针，避免把环境错误误判为模型失败。

### Q16：如果进入生产，还缺什么？

需要真实匿名故障样本、独立 holdout、并发和长时压测、网络与数据库故障演练、幂等控制、
RBAC/Document ACL、审计告警和 SLO。当前结果只证明单机合成集上的控制策略。

## 4. STAR 失败案例

### Situation

Flash 已通过，但 Pro 原始 20 题恢复率只有 66.67%，安全终止虽然正常，恢复质量未达门槛。

### Task

在不修改冻结题目和评分器、不增加无限重试的前提下，提高 Pro 恢复率并保持安全硬门槛。

### Action

按失败轨迹聚类；增加无损参数归一；将预算从按 Tool 计数改为请求共享；对隔离瞬时故障
增加一次可审计自动恢复；对首次 terminate 增加证据门禁；让报告超时返回 partial；补充
回归测试并用新目录完整跑 20 题。

### Result

恢复率 66.67%→91.67%，总通过率 70%→90%，完成状态准确率 75%→95%，P95 延迟
115.30 秒→48.43 秒；终止率保持 100%，盲重试和断路后调用保持 0%。

## 5. 面试时必须主动披露

- 后一次是查看失败后的同集修复回归，不是独立盲测。
- 自动恢复仅用于隔离故障注入；生产不会凭空制造或吞掉真实故障。
- 原始 66.67%、无效环境轮和安全指标回退轮均保留。
- 20 题合成集不能代表生产 SLO 或跨业务泛化。
- 当前仍有一条可恢复任务失败，下一步应使用全新 holdout 验证。
