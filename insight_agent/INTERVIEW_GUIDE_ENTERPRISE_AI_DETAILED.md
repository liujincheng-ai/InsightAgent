# InsightAgent 完整面试文档（央国企 AI 岗）

## 1. 面试定位

这套讲法重点是企业数据与制度协同、业务口径、安全边界、证据追溯、可重复部署和可验收性。必须明确 V1 是可私有化演进的单机原型，不是已在真实单位上线的生产系统。

## 2. 3 分钟讲稿

InsightAgent 是一个企业经营数据与知识协同分析智能体，使用汽车配件销售作为垂直验证。传统经营分析中，销售事实在数据库，管理规则在制度文档，分析人员需要人工写 SQL、核对口径、查制度和整理报告。本项目用 InsightAgent 和 DeepSeek 将这些步骤组织为可追溯的 Agent 链路。

数据层包含 4 张业务表和 60,000 条合成销售明细，固定随机种子，通过 Gold Truth 校验销售额、渠道贡献、客户下降和毛利变化。知识层包含 6 份带章节号的合成企业制度，在本地使用中文 Embedding 和 ChromaDB。

我在 InsightAgent 的统一 Tool 体系中实现了销售诊断、客户流失预警和经销商健康度 3 个业务 Tool。为了避免模型编数，所有核心数值来自参数化只读 SQL 或 Tool Observation；数据事实、演示规则和经营建议分层表达。

安全方面，不把 Prompt 当成安全边界。Tool 使用独立 PostgreSQL 只读角色、短连接和只读事务，通用 SQL 还有单语句只读预检；数据库错误会脱敏，权限和未知错误不重试，Key 和密码只由运行时环境变量提供。

项目有 30 条冻结验收集，Pro 任务通过率由 26/30 提升到修复候选的 30/30；独立首次发布复验冻结为 28/30，其中 SQL 执行、Tool、制度引用和综合任务均为 100%。主链路严格稳定性由 0/5 到 5/5，迭代后累计 214 项自动化测试通过。Week 2 首次 Pro Tool Calling 为 14/40，修复文本 ReAct 协议后同集复验 38/40。这是合成数据上的原型验收；后一次不是独立盲测，我不会把它夸大为生产系统或完全离线方案。

## 3. 8 分钟讲稿

### 3.1 业务问题

主问题需要同时回答“降了多少”、“哪些渠道和客户贡献最大”、“根据什么制度干预”。如果只做数据库问答，没有制度根据；如果只做 RAG，没有当期经营事实；因此采用数据与知识协同。

### 3.2 数据口径和可复现性

合成数据从 2025-01-01 到 2026-06-30，主异常只植入华东、刹车系统、2026Q2 和经销商渠道，同时设置华南增长的对照。销售额、毛利、加权毛利率、下降贡献和客户预警都有明确公式。数据可以从空表重新生成并得到同一指纹。

### 3.3 知识库和引用

制度文档带章节号，评测不只看答案文字是否相似，而是分开记录目标文档是否进入 Top-K、引用章节是否正确、结论是否被条款支持。综合任务如果证据不足，通过受控 `semantic_search` 定向恢复，不直接编造条款。

### 3.4 权限和凭据边界

数据库 owner 只用于初始化；Agent Tool 只使用 `insight_readonly`。应用侧参数化 SQL 和预检减少误用，数据库权限提供最终写入阻断。启动脚本使用 SecureString 读取 Key 和密码，配置只引用环境变量。

### 3.5 数据流转边界

PostgreSQL、ChromaDB 和 BGE Embedding 在本地，但 DeepSeek 是 API 模式。所以模型 Prompt 中携带的 Schema、查询结果摘要或检索 Context 会发送到远程模型。完全离线需要替换为本地 LLM，并重新验证效果和算力。

### 3.6 验收和提升

Day 5 的 Pro 基线是 26/30。失败不是统一的“模型不准”，而是 SQL 预检误拒、事实转写错误、Tool 选择漂移和虚假完成。修复是按层次做的：修正 SQL 别名解析；将高风险数值绑定到 Observation；强制直接业务 Tool；将报告完成与真实 Tool/检索/HTML 事件绑定；再扩展常见查询结果形状。修复候选完整运行曾为 30/30；独立首次发布复验为 28/30，我保留两项事实完整性/口径失败，没有选择性重跑。

## 4. 15 分钟深讲路线

1. 2 分钟：企业问题、项目边界和主问题。
2. 2 分钟：数据模型、异常植入、Gold Truth 和合成数据合规性。
3. 2 分钟：6 份制度、切块、Embedding、ChromaDB 和章节引用。
4. 3 分钟：数据库只读角色、参数化 SQL、错误脱敏和有限恢复。
5. 2 分钟：三个 Tool 如何将业务口径变成可验收契约。
6. 2 分钟：30 题 Benchmark、26/30→候选 30/30→首次发布复验 28/30、0/5→5/5 和失败归因。
7. 2 分钟：当前非完全离线、非生产级的边界，以及 RBAC/ACL/审计路线。

## 5. 高频问题与参考回答

### Q1：为什么同时需要数据库和知识库？

数据库回答“发生了什么”，制度回答“应按什么规则处理”。两者需要通过同一任务的证据链绑定，不能只把两段文本拼在一起。

### Q2：本地 Embedding 是否等于完全私有化？

不等于。文档向量化和存储在本地，但送入 DeepSeek API 的 Context 仍会离开本机。完全离线必须替换本地 LLM 并重新评测。

### Q3：为什么 Prompt 不是安全边界？

模型可能违反 Prompt，恶意文档也可能做 Prompt Injection。写入阻断必须落在参数校验、SQL 预检和数据库只读权限上。

### Q4：只检查 SQL 是否以 SELECT 开头够吗？

不够，多语句、注释、修改型 CTE 和数据库特定语法都可能绕过简单前缀。应用侧校验只是一层，最终依赖最小权限账号。

### Q5：为什么 owner 和 Agent 账号要分开？

owner 用于建表和导入，Agent 只需要查询。分开后即使应用检查失效，数据库仍会拒绝写入。

### Q6：审计一次 Agent 任务应记录什么？

生产版应记录 user_id、run_id、问题摘要、Tool、参数摘要、SQL、文档 ID/章节、模型、延迟、Token、状态和时间；不记 Key、密码和不必要的敏感原文。V1 只有评测轨迹，不声称已完成企业审计系统。

### Q7：RBAC 和 Document ACL 有什么区别？

RBAC 根据角色授予能力，Document ACL 决定具体文档或密级是否可见。权限过滤应在 Retrieval 之前落到候选集，不是先把无权文档放入 Context 再删除。

### Q8：为什么客户 Tool 只叫“流失预警”？

交易数据只能证明停止采购或大幅下滑，不能证明合作关系已终止。确认流失还需沟通、库存、价格和售后证据。

### Q9：经销商健康度为什么不用机器学习？

没有真实的违约、流失或恶化标签，训练模型无法可靠验证。V1 规则可解释、可回放，但必须标注为演示规则；有真实标签后再比较召回、准确、校准和干预收益。

### Q10：怎样确保制度引用可追溯？

文档有章节号，检索结果保留文档与 `primarySection`，SSE、历史和最终引用均保留来源。评测分开判定文档命中和章节准确。

### Q11：为什么需要 Gold Truth？

如果没有预先冻结的业务事实，模型失败后容易反向修改答案。Gold 来自数据库独立计算和制度原文，使验收有稳定尺度。

### Q12：30/30 说明了什么？

说明在固定 InsightAgent、模型配置、合成数据和 30 条冻结题上，修复候选完成了验收契约。它不说明真实生产分布、并发、权限和长时运行已通过。

### Q13：Docker Compose 是否等于生产部署？

不等于。它只能证明依赖和环境可重复，不自动提供高可用、弹性、密钥管理、灾备和运维体系。V1 应称单机交付原型。

### Q14：如何应对 Prompt Injection？

文档内容是低信任证据，不能改写系统指令或 Tool 权限。生产版还需要检索前 ACL、Tool 最小权限、输入/输出检测和审计。

### Q15：进入生产前还缺什么？

真实匿名数据与标签、用户/部门权限、检索前 ACL、全链路审计、秘钥托管、安全沙箱、并发与容量评估、监控告警、备份恢复、模型及数据变更流程。

## 6. 指标提升的完整回答

面试官问“你是怎么从 86.67% 做到候选 100% 的”时，先说它们是同一固定 30 题集上的两次完整运行，再主动补充独立首次发布复验为 93.33%，然后按失败层次回答：

1. SQL 预检误拒：修复 JOIN/派生表别名识别，保持只读约束。
2. 事实转写错误：从成功 Observation 确定性计算和渲染核心指标。
3. Tool 选择漂移：用业务意图路由和 ToolPack 限制首个领域 Tool，只允许窄形状恢复。
4. 虚假完成：将完成状态绑定到领域、制度和 HTML 真实事件。
5. 查询形状漂移：扩展季度、毛利、渠道和客户别名，对缺列结果失败关闭。
6. 验证：先定向回归，再重新运行全部 30 题；保留失败轨迹，不改 Gold。

首次发布复验的两项失败应主动解释：一个只返回毛利率变化值而未返回两个基准毛利率，另一个把“下降贡献”分母解释为所有负向渠道之和而非区域净下降。它们说明企业指标必须有显式口径字典和结构化输出契约，不能只依赖自然语言提示。

## 7. 现场展示顺序

1. README 的业务价值、数据流转和已知限制。
2. `schema.sql`、`anomaly_ledger.json` 和 6 份制度。
3. `tools/db.py` 的只读连接与三个 Tool 的参数化 SQL。
4. `sales_diagnosis_gate.py` 和 `domain_policy.py` 的完成门禁、错误脱敏。
5. 冻结数据集、验收报告和累计 214 项回归，以及 Week 2 Pro 14/40 → 同集修复回归 38/40 的公开轨迹。
6. 最后主动说明非完全离线、非生产上线案例的边界。

## 8. 表达禁区

- 不说“已为某央企上线”或“服务多部门”。
- 不说“生产级权限和审计已完成”。
- 不说“数据完全不出域”，因为使用远程 DeepSeek API。
- 不把本地 Embedding 说成完全私有化。
- 不把预警结果说成已确认流失或处罚依据。
- 不把 30/30 说成真实生产准确率。

## 9. Week 1：指标治理与歧义门禁

Week 1 将销售额、销量、加权毛利率、同比/环比、净下降贡献等口径沉淀为 YAML 业务词典，并显式区分交易区域和客户所属区域。语义资产可版本化，数据库侧提供只读视图，应用侧对高风险歧义先澄清且不开放 SQL，形成 Prompt、应用门禁、数据库权限三层控制。

30 条专项集的唯一一次 Pro 最终运行是 27/30（90%）：SQL 执行、歧义处理和澄清前不查库均为 100%，但严格结果集 76.92%、答案事实 88.46%。这组指标适合说明治理价值，也必须同时说明数据为合成、小样本不具统计代表性、三个失败仍未解决，以及远程模型不满足完全不出域。
