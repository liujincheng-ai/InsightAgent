# InsightAgent Day 4 面试准备指南

## 1. 一分钟项目讲解

Day 4 把 InsightAgent 从单一销售诊断能力扩展为三个职责清晰的领域 Tool。客户流失
Tool 对当前季度和上一季度做客户级对比，识别停止采购或大幅下滑预警并计算下降贡献；
经销商健康度 Tool 使用销售、活跃采购天数、折扣和毛利率四个可解释维度评分。三个
Tool 都通过 InsightAgent 原生 `@tool`、`FunctionTool`、`ResourceManager` 和 `ToolPack`
进入 ReAct Agent，没有另建旁路 Agent。路由门禁根据问题意图只允许正确的领域 Tool
先执行，综合报告再继续检索相关制度并生成 HTML。

## 2. 高频面试题与参考回答

### Q1：为什么拆成三个 Tool，而不是一个万能分析函数？

参考回答：销售诊断、客户风险和经销商评分的输入、输出及失败语义不同。拆分后每个
description 更聚焦，模型选择更容易，单元测试也能围绕一个业务契约展开。季度解析、
安全除法和评分函数仍集中在 `metrics.py`，数据库访问集中在 `db.py`，所以拆分职责
没有导致基础逻辑复制。

追问：Tool 是否越多越好？

不是。Tool 数量增加会扩大 Action Space、增加 Prompt token 和误选机会。只有出现
独立的输入输出契约、业务规则和错误语义时才拆 Tool，并用三类固定问题的路由测试
验证收益。

### Q2：为什么客户 Tool 不直接输出“已流失客户”？

参考回答：交易数据只能证明客户停止采购或大幅下滑，不能证明合作关系已经结束。
《重点客户流失预警办法》2.2 明确要求数据异常必须人工核实。因此代码使用
`suspected_churn` 和 `significant_decline`，Observation 也明确提示核对沟通、库存、
价格和售后事实。这体现了事实、预警和管理判断的边界。

追问：如果业务坚持叫“流失客户”怎么办？

可以保留用户熟悉的 Tool 名称，但返回字段和报告措辞仍应区分“预警”与“确认”。
确认流失需要新增状态字段、责任人核验记录和可审计的关闭流程。

### Q3：客户下降贡献度如何计算？

参考回答：先在同一区域、品类和两季度范围内按客户聚合销售额；客户下降额为上一季度
减当前季度，区域总净下降额为所有客户上一季度合计减当前季度合计。贡献度是客户正向
下降额除以区域总净下降额。如果区域没有净下降，分母无业务意义，返回 `null` 而不是
零或无穷大。

追问：为什么不用所有下降客户下降额之和作为分母？

那会忽略增长客户的抵消效果，回答的是“下降客户内部构成”，而不是“对区域净下降的
贡献”。两种口径都可以存在，但必须命名清楚；当前 Tool 固定采用区域净下降口径。

### Q4：为什么基准期固定为上一季度？

参考回答：Tool 的 V1 契约就是季度经营监控，上一季度能回答短期经营变化，而且与
`current_quarter` 单参数保持一致。同比仍可作为其他 Tool 的补充指标。如果让模型自由
选择基准期，同一个问题可能产生不同结果，不利于 Gold Truth 和回归测试。

### Q5：健康度为什么不用机器学习？

参考回答：当前是合成数据，没有真实的违约、流失或经营恶化标签。训练模型既无法可靠
评估，也很难向经营人员解释。规则评分能够逐项展示扣分原因、对应制度阈值并复现结果。
有真实标签后，可以用监督模型与规则基线比较准确率、召回率、校准度和业务干预收益，
而不是直接替换规则。

### Q6：四项权重和分段从哪里来？

参考回答：40/20/20/20 权重来自项目 V1 设计；折扣的 8%、12%、15% 分段直接来自
价格制度。销售、活跃度、毛利变化和 high/medium/low 分段是明确版本化的演示规则，
不是制度原文或行业标准。项目把两类来源写入 `DAY4_RULES.md`，避免把人为设计包装成
公司政策。

追问：生产系统如何确定权重？

先与业务共同定义结果标签和干预目标，再用历史回测、专家评审、敏感性分析及阈值稳定
性确定；规则版本、变更原因和生效时间需要审计记录。

### Q7：毛利率为什么不能平均每笔毛利率？

参考回答：不同订单金额不同，简单平均会让小额订单和大额订单拥有同等权重。项目使用
总毛利除以总销售额的加权毛利率，与《2026 年度经营目标》2.2 一致。零销售额时返回
`null`，不伪造 0% 毛利率。

### Q8：折扣为什么使用订单行简单平均？

参考回答：《汽车配件价格与折扣管理办法》2.2 明确规定制度监控默认采用订单行简单
平均。这里没有自行换成金额加权；但输出必须写明口径，因为两种算法回答的问题不同。

### Q9：如何保证数据库安全？

参考回答：业务 Tool 的 SQL 是代码中的常量，不接收模型生成的 SQL；所有业务参数使用
DB-API 参数绑定。连接使用独立 `insight_readonly` 角色和只读事务，每次查询短连接，
驱动异常只向 Agent 返回异常类型，不暴露主机、密码或原始连接串。权限验证证明该角色
可 SELECT，但不能 INSERT、UPDATE 或 DELETE。

### Q10：如何防止模型乱填 Tool 参数？

参考回答：第一层是 FunctionTool 暴露的类型 Schema；第二层校验季度 `YYYYQn`、
`top_n` 1～20、下降阈值大于 0 且不超过 1；第三层是数据库业务范围。非法输入统一返回
`status=error`、错误码和空 evidence，不静默修改参数，也不把值拼进 SQL。

### Q11：Agent 如何选择三个 Tool？

参考回答：Tool description 提供语义选择，服务端再用轻量意图规则确定当前问题必须先
执行的领域 Tool。门禁在该 Tool 完成前阻止另外两个领域 Tool 和无关动作。客户流失、
经销商健康和销售诊断的三道固定题分别验证首个领域动作。这个门禁仍是原生 ToolPack
子类，不是旁路执行器。

追问：关键词路由是否脆弱？

是，V1 规则适合固定演示，但生产中应使用结构化意图分类、置信度和歧义回退，并建立
改写题、同义词和多意图 Benchmark。规则的价值是提供可验证的最低正确性边界。

### Q12：为什么 4.2 节不能写死在所有 Prompt 中？

参考回答：4.2 是 A 级经销商连续下降处置，只适用于对应问题。Day3 固定主 Demo 正好
符合该范围，但 Day4 增加新问题后，通用硬编码会让客户流失或产品质量问题引用错误制度。
因此现在按领域意图映射制度：客户风险使用客户预警办法，经销商评分使用 3.1/3.2，
涉及 A 级下降处置时才增加 4.2；无关销售报告要求检索对应制度而非固定章节。

### Q13：单 Tool 问题与综合报告的执行链有什么区别？

参考回答：单 Tool 问题在获得正确 Observation 后即可组织答案并终止，减少无关检索和
HTML 成本。包含制度、整改建议、引用、图表或报告意图的问题进入完整证据链：领域 Tool、
相关制度检索、HTML 报告。两者共享同一 ReAct Runtime，只是完成条件不同。

### Q14：如何处理无数据和零基准？

参考回答：整个范围无数据时返回 `status=no_data`。除法分母为零时比例返回 `null`；
健康度对“基准期无采购、当前期有采购”和“两期都无采购”分别处理。Agent 必须说明
无法比较，不能把 `null` 改写成 0%，因为 0% 表示已计算且没有变化。

### Q15：如何保证计算和排序可复现？

参考回答：时间窗口使用左闭右开日期；SQL 固定并参数化；金额使用 Decimal 四舍五入；
率统一保留四位小数；风险排序依次使用风险级别、健康度升序、当前销售影响降序和名称。
Gold Truth 固定在版本化 JSON 中，测试不比较 SQL 字符串答案，而比较关键事实和契约。

### Q16：Day4 如何测试？

参考回答：测试分三层。纯函数测试覆盖所有评分边界；Service 测试用 FakeExecutor 验证
SQL 参数化、业务分类、错误与排序；集成测试验证 Prompt 和 ToolPack 的首个领域动作。
最后使用真实 PostgreSQL 对 Gold Truth，并在 Web UI 用 DeepSeek 跑三道题，保存截图、
Tool JSON 和轨迹。当前自动化结果为 81 passed，Ruff 全通过。

## 3. 源码讲解路线

面试演示建议按下面顺序打开文件：

1. `insight_agent/DAY4_RULES.md`：先说明制度规则与演示规则边界；
2. `insight_agent/tools/metrics.py`：展示纯函数和零分母处理；
3. `insight_agent/tools/customer_loss_analysis.py`：展示客户聚合、分类和贡献；
4. `insight_agent/tools/dealer_health_analysis.py`：展示四项评分与扣分解释；
5. `insight_agent/tools/db.py`：展示只读账户、只读事务和错误脱敏；
6. `insight_agent/agent/sales_diagnosis_gate.py`：展示意图选择与门禁状态；
7. `packages/dbgpt-app/src/dbgpt_app/component_configs.py`：展示 ResourceManager 注册；
8. `agentic_data_api.py`：展示原生 Web ReAct ToolPack 的组装；
9. `tests/insight_agent/`：展示边界、路由与回归证据；
10. `insight_agent/evidence/day4/`：展示真实数据库和 Web UI 结果。

## 4. 容易答错的点

- 不要说“模型判断客户已经流失”，要说“确定性规则产生待核验预警”。
- 不要说“健康度是行业标准”，要说明权重和部分分段是 V1 演示规则。
- 不要说“折扣按金额加权”，制度要求订单行简单平均。
- 不要说“毛利率取订单平均”，项目用总毛利除以总销售额。
- 不要把 Tool description 说成唯一路由保障；还有服务端意图选择和 ToolPack 门禁。
- 不要声称系统分析了回款和投诉；当前 Schema 没有这些事实。
- 不要把 4.2 节强制套到所有问题；它只适用于 A 级经销商连续下降处置。
- 不要只报测试数量；说明纯函数、Service、路由、真实数据库和 Web UI 各验证什么。
