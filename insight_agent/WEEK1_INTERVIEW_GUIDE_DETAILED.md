# Week 1 Text-to-SQL 语义正确性面试详解

## 1. 30 秒项目陈述

我在 InsightAgent 的 ReAct 数据分析链路上增加了一层可审计的业务语义控制。它把销售额、销量、加权毛利率、同比/环比和下降贡献等口径从零散 Prompt 提示升级为 YAML 业务词典，并在 SQL 前做通用语义预检；对指标、时间或区域维度会改变结论的模糊问题，系统先澄清且不开放 SQL Tool。我另外构建了 30 条冻结语义集，分别评估 SQL 执行、结果集、答案事实和歧义处理。唯一一次 Pro 最终运行是 27/30，SQL 执行和歧义门禁都是 100%，同时完整披露三个失败。

## 2. 两分钟项目陈述

Day 7 的系统已经能稳定调用数据库、RAG 和领域 Tool，但一次最终复验仍出现两个典型问题：SQL 结果有 Q1/Q2 毛利率，回答却漏了事实；渠道下降贡献使用了错误分母。这说明 Text-to-SQL 的核心并不是语法，而是业务指标、维度、时间和最终表达的一致性。

我把问题拆成四层。第一层是语义资产，用 YAML 维护指标公式、同义词、Schema 字段、日期半开区间和歧义规则。第二层是运行时控制，按问题只选择相关语义；高风险歧义题不挂 SQL Tool；非歧义题在只读预检中检查 Join、范围、去重和加权公式。第三层是数据库层，建立按交易区域和客户区域聚合的两个只读语义视图。第四层是评测，冻结 18/8/4 三个 Split，严格分开 SQL 是否执行、结果表是否命中、最终答案事实是否完整，以及澄清前是否查库。

最终 Pro 唯一运行 27/30，Day 7 两个回归题 2/2。三个剩余失败分别是百分比表达、数据覆盖范围和不存在实体处理。这些失败说明下一阶段应做结果类型化和实体链接，而不是继续堆 Prompt。

## 3. 为什么需要业务语义层

数据库 Schema 只能说明字段叫什么，不能完整表达业务口径。例如：

- “销量”是 `SUM(quantity)`，不是销售额，也不是订单行数。
- “加权毛利率”是 `SUM(gross_profit) / SUM(sales_amount)`，不能 `AVG(gross_margin)`。
- “渠道对净下降的贡献”分母是同范围全渠道的 Q1−Q2 净下降，不是只对下降渠道求和。
- “区域”既可能指交易发生区域，也可能指客户所属区域。
- Q2 应使用 `[2026-04-01, 2026-07-01)`，半开区间避免时间戳边界错误。

如果这些知识只存在于模型常识里，SQL 语法完全正确也可能给出错误经营结论。语义层把它们变成可审计、可测试、可版本化的工程资产。

## 4. 架构与调用链

请求进入 `agentic_data_api.py` 后，系统读取 `ext_info.semantic_profile`。`semantic/layer.py` 根据问题命中相关指标、Schema 说明和歧义规则：

1. 若为高风险歧义，生成确定性澄清项，ToolPack 只保留终止工具，不开放 SQL。
2. 若可查询，把相关语义拼入 Agent Prompt。
3. 模型生成 SQL 后，`domain_policy.py` 做业务范围和公式预检。
4. SQL 通过 InsightAgent 数据源执行；数据库账号是 `insight_readonly`。
5. 成功 Observation 进入最终回答；高风险指标由确定性呈现逻辑复算或补充解释。

这里用了 Prompt、应用门禁和数据库权限三层控制。Prompt 提供行为引导，应用层拒绝不合规动作，数据库只读角色是最终边界。

## 5. 关键设计问答

### Q1：为什么不用一段很长的 Prompt？

全量 Prompt 会带来无关噪声、上下文成本和规则冲突，也不便于版本化。当前实现先用同义词和问题特征选择相关指标及规则，再生成短的语义上下文。YAML 是配置资产，Python 负责选择和门禁，各自职责清晰。

### Q2：为什么歧义题不让模型先查库看看？

“哪个区域最好”缺少指标和时间。任何一次查询都会暗中选择口径，查询结果可能诱导后续回答。澄清前移不仅减少浪费，还避免把默认假设伪装成用户意图。因此代码层直接不挂载 SQL Tool，而不是只在 Prompt 中写“请先询问”。

### Q3：哪些歧义需要澄清？

只拦截会显著改变经营结论的高风险歧义：指标缺失、时间/同比环比基准缺失、交易区域与客户区域不清、排名周期缺失。低风险格式问题可使用已公开默认值，避免所有问题都反问。

### Q4：为什么建立语义视图？

视图提供稳定的聚合入口，减少重复 Join 与日期抽取，也显式区分交易区域和客户归属区域。它不是万能答案：复杂排名和贡献分析仍可能需要基础表或 CTE；视图必须受同一只读权限控制。

### Q5：为什么仍要 SQL 预检？

词典只告诉模型正确做法，不能保证每次遵循。预检检查已知区域/品类/渠道是否在 SQL 中保留、同比年份是否齐全、销量是否真的聚合 quantity、加权指标是否用正确分子分母、不同客户是否 `COUNT(DISTINCT ...)`。它是执行前的可测量防线。

### Q6：预检为什么不能硬编码某一道题？

题目到固定 SQL 的映射会让 Benchmark 虚高且无法泛化。实现只检查可复用的不变量，例如“加权毛利率必须是总毛利除总销售额”，不会按 `w1-test-02` 返回预制 SQL 或答案。

### Q7：为什么多条 SELECT 被归为可重试语法错误？

执行入口坚持单语句。模型偶尔把两个候选 SELECT 一起提交，这不是数据库权限问题，而是输出形状错误，因此应在执行前阻断并允许本步骤一次纠正。DML/DDL 或只读权限违规仍是不可重试，不能因为重试机制放宽安全边界。

### Q8：结果集准确率为什么比总通过率低？

严格结果集要求 Observation 表包含 Gold 的列和值；总通过允许最终答案基于已验证 Observation 完整给出语义事实。例如 SQL 可能返回 Q1/Q2 原始值并在答案中正确计算变化率，结果形状未完全匹配 Gold，但用户事实正确。两者都要报告，不能用一个指标掩盖另一个。

### Q9：怎么防止评分器把 `0.2613` 和 `26.13%` 判成不同？

评分器对比例/百分比做单位归一化，同时保留数值容差。该规则只用于等价表示，不会把百分比与百分点混为一谈。百分点是两个百分率的算术差，需要独立 Gold 事实。

### Q10：如何保证重评分没有篡改结果？

原始目录保存每题 SSE events、模型答案和 SQL。重评分前后对 events 做序列化一致性断言，Manifest 声明不可变字段；工具只重写派生 Verdict、汇总和 CSV。最终报告还记录了评分器 V2 的修正原因。

## 6. 评测设计

### Split

- dev 18：开发期可见，用于覆盖基本语义和通用修复。
- test 8：冻结后只用于泛化验收。
- challenge 4：全部为高风险歧义，要求先澄清且不执行 SQL。

### 指标

- SQL execution：验证运行链路，不代表语义正确。
- strict result set：验证表格形状和值。
- answer facts：验证最终答案对用户要求的事实完整性。
- ambiguity handling：验证澄清要点。
- no SQL before clarification：验证门禁真正生效。

### 最终结果

Pro、temperature 0、combined、30 题唯一最终运行：27/30（90%）；SQL 执行 100%，严格结果集 76.92%，答案事实 88.46%，歧义与澄清前不查库均 100%，平均 6.35 秒。Day 7 回归 2/2，下降贡献 2/2，加权毛利率 2/2。

## 7. 如何讲消融实验

系统支持 baseline、comments、glossary、combined 四种 Profile。Flash 的单次探索中，当前实现对照为 23/30，comments 22/30，glossary 25/30，首轮 combined 23/30；后续 combined 两次为 26/30 和 24/30。

面试时必须说明：这些是单次路径观测，不足以证明某个组件的因果增益。temperature 0 并不保证远程推理完全确定。更严谨的实验应固定服务代码和数据指纹，每个配置多次运行，报告均值、方差、配对题目变化和置信区间。

## 8. 三个失败怎么回答

### 加权折扣率

SQL 和结果集正确，但答案只给 `0.1041...`，没有写 10.41%。根因是展示层缺少单位类型，不是数据库计算错误。改进方向是让结果 Schema 携带 `ratio/percent/currency/count` 类型并统一格式化。

### 2027 Q1 无数据

`COALESCE(SUM, 0)` 抹平了“无记录”和“真实为零”。答案没有指出数据截止到 2026-06-30。改进方向是返回行数、数据覆盖范围和三态状态，而不是只返回一个数。

### 不存在品类

模型把字面上的不存在实体解释成维表孤儿记录，并提交了多条 SELECT；预检正确阻断，但没有恢复到“按品类名过滤，0 行，明确无数据”。改进方向是实体链接和候选值校验，而不是为该题硬编码。

## 9. 可能的追问

### 如果上线，优先补什么？

第一优先是类型化结果合同和无数据三态，因为它直接影响用户是否误判 0；第二是实体链接与维度值校验；第三是扩大真实脱敏评测；之后才是性能和成本优化。权限、审计和租户隔离则是企业上线的并行前置项。

### 为什么不微调模型？

现阶段错误集中在少量明确业务约束和输出合同，配置、门禁和确定性代码更低成本、更可解释。等积累大量稳定标注、Schema 多样性和错误分布后，再评估微调或专用 Text-to-SQL 模型。

### 怎样支持多个行业？

保留通用运行时、评分协议和安全门禁，把词典、实体类型、语义视图及领域 Tool 做成租户/行业包。每个包有独立版本、Owner、变更审批和回归集，不能把汽车配件规则直接泛化到其他行业。

### 语义层如何治理？

每个指标需要唯一 ID、中文名/同义词、公式、粒度、允许维度、时间口径、单位、Owner 和版本。变更必须触发受影响题集回归；废弃指标要保留兼容期；最终 SQL 和使用的语义版本进入审计日志。

## 11. 面试现场演示建议

1. 先问“哪个区域最好”，展示系统提出指标和时间澄清，且轨迹无 SQL。
